# 03 · 认证与权限

> 本篇覆盖：JWT + Redis 登录态双校验（为什么 JWT 无状态还要 Redis）、JwtUtil（jjwt 0.13）、JwtAuthenticationFilter（Bearer 解析 / Redis 校验 / 角色加载 / FilterRegistrationBean 防二次注册）、SecurityConfig（无状态会话 / 白名单精确优先 / 401 JSON EntryPoint）、@EnableMethodSecurity + @PreAuthorize、BCrypt。
>
> **学习目标**：理解"JWT 为什么需要 Redis""Spring Security 过滤链执行顺序""BCrypt 为什么每次结果不同"，并能在面试中讲清认证授权的完整链路。

---

## a. 这个模块是干嘛的

认证回答"你是谁"，授权回答"你能干什么"。CityGo 用 JWT 做无状态令牌，用 Redis 做服务端登录态（token → userId），用 Spring Security 做请求拦截与角色校验，用 BCrypt 做密码加密。用户登录拿到 token 后，每次请求带 `Authorization: Bearer xxx`，过滤器解析校验后把身份写进 SecurityContext，`@PreAuthorize("hasRole('MERCHANT')")` 再拦一层角色。这一篇是**面试最高频考点之一**。

## c. 先懂概念

1. **JWT**：三段式令牌（Header.Payload.Signature），服务端不存状态，靠签名校验真伪，Payload 里放 userId、username 等声明。
2. **无状态 vs 有状态**：纯 JWT 是"无状态"的（服务端不存 session）；CityGo 是"JWT + Redis"混合：JWT 承载身份，Redis 存登录态，实现"可主动失效"。
3. **BCrypt**：带盐的慢哈希算法，每次加密结果不同（盐随机），校验靠 `matches(raw, hashed)`，强度参数 10 表示 2^10 次迭代。
4. **SecurityContextHolder**：Spring Security 的线程级上下文，认证成功后把 `Authentication` 写进去，Controller 里 `getAuthentication().getPrincipal()` 取 userId。
5. **FilterRegistrationBean**：把已交给 SecurityFilterChain 管理的过滤器从 Servlet 容器注册里禁用，防止执行两次。

## d. 逐个详解

### 1. JwtUtil：jjwt 0.13 新 API

构造器从配置注入 `citygo.jwt.secret` 和 `citygo.jwt.expire-seconds`，`Keys.hmacShaKeyFor(secret.getBytes(UTF_8))` 生成 HS256 密钥。注释强调密钥至少 32 字节（HS256 要求）。

- **生成** `generateToken(Long userId, String username)`：`Jwts.builder().subject(String.valueOf(userId)).claim("username", username).issuedAt(now).expiration(expiry).signWith(key).compact()`。subject 放 userId，username 放自定义 claim。
- **解析** `parseUserId(String token)`：`Jwts.parser().verifyWith(key).build().parseSignedClaims(token).getPayload().getSubject()`，返回 Long。

坑（类注释点名）：jjwt 0.13 用 builder/parser 风格，**严禁用旧版已废弃的 `setSubject` / `parseClaimsJws`**。0.13 的 `signWith(key)` 直接传 SecretKey，不需要再传签名算法。

#### JWT 结构详解

```
Header.Payload.Signature

Header: {"alg":"HS256","typ":"JWT"} → Base64Url
Payload: {"sub":"1892345678901234567","username":"zhangsan","iat":1234567890,"exp":1234571490} → Base64Url
Signature: HMACSHA256(base64Url(header) + "." + base64Url(payload), secret)
```

**注意**：Payload 只是 Base64Url 编码，**不是加密**，任何人都能解码看到内容。所以 JWT 里不能放敏感信息（如密码）！

### 2. JwtAuthenticationFilter：JWT + Redis 双校验与角色零查库缓存

继承 `OncePerRequestFilter`（保证单请求只过一次）。核心流程 `doFilterInternal`：

1. 取 `Authorization` 头，非 `Bearer ` 前缀直接放行（不认证）；
2. `jwtUtil.parseUserId(token)` 解析 JWT，非法/过期则放行，由入口点统一 401；
3. **Redis 校验**：`stringRedisTemplate.opsForValue().get(LOGIN_TOKEN_PREFIX + token)`，key 不存在或值前缀不等于 userId 视为已登出，放行；
4. **角色解析（零查库性能优化）**：登录时 Redis 存入的值为 `userId:ROLE1,ROLE2` 格式，过滤器直接从冒号后解析出角色列表并映射为 `ROLE_xxx` 的 `SimpleGrantedAuthority`（老格式或未命中则降级 `loadAuthorities(userId)` 查库），**彻底消除每个请求都需要查 user_role 和 role 表的 2 次数据库 I/O 性能瓶颈**；
5. 构建 `UsernamePasswordAuthenticationToken(userId, null, authorities)` 写入 SecurityContext，并把原始 token 透传到 `request.setAttribute(REQUEST_ATTR_TOKEN, token)`。

#### 为什么 JWT 无状态还要 Redis？

这是**面试必问**。纯 JWT 一旦签发，在过期前无法主动失效——用户点"退出登录"、管理员禁用账号、用户改密码，旧 token 依然有效。CityGo 把 `token → userId:roles` 写进 Redis，登出即删 key，实现**服务端可控的登录态**；JwtAuthenticationFilter 里"JWT 签名 + Redis 存在性"双校验，任一不满足都算未认证。

**JWT 解决"身份自证"，Redis 解决"可撤销"。**

#### 认证 vs 授权 的区别

| 维度 | 认证（Authentication） | 授权（Authorization） |
|------|----------------------|----------------------|
| 回答的问题 | "你是谁？" | "你能干什么？" |
| 发生时机 | 请求进来时（Filter 层） | 认证通过后（方法层） |
| 失败响应 | 401 未登录 | 403 无权访问 |
| CityGo 实现 | JwtAuthenticationFilter | @PreAuthorize |

#### REQUEST_ATTR_TOKEN 的作用

登出接口 `/api/auth/logout` 需要拿到原始 token 才能删 Redis key，但 token 在 Authorization 头里，过滤器解析后把 token 塞进 request attribute，`AuthServiceImpl.logout` 再取出来删。

### 3. SecurityConfig：无状态 + 白名单精确优先

- `@EnableWebSecurity` + `@EnableMethodSecurity`（开启方法级 `@PreAuthorize`）。
- `csrf.disable()`：JWT 无 Cookie 会话，无 CSRF 攻击面。
- `sessionManagement.sessionCreationPolicy(STATELESS)`：不创建 HttpSession。
- 白名单顺序（**精确规则必须放在通配规则之前**）：

```java
.requestMatchers(HttpMethod.GET, "/api/shops/my", "/api/products/my").authenticated()  // 先精确声明
.requestMatchers("/api/auth/register", "/api/auth/login").permitAll()
.requestMatchers("/api/merchants/register").permitAll()
.requestMatchers("/api/categories").permitAll()
.requestMatchers(HttpMethod.GET, "/api/coupons").permitAll()
.requestMatchers("/api/search/**").permitAll()
.requestMatchers(HttpMethod.GET, "/api/shops/**").permitAll()
.requestMatchers(HttpMethod.GET, "/api/products/**").permitAll()
// ... swagger / actuator / OPTIONS 放行
.anyRequest().authenticated()
```

#### 坑：匹配顺序（面试高频）

Spring Security 的 `authorizeHttpRequests` **按声明顺序匹配，第一条命中即生效**。`/api/shops/my` 和 `/api/products/my` 本身是 GET，若不提前声明，会被下方的 `GET /api/shops/**` 通配放行误伤——"我的店铺""我的商品"这类本应登录的接口就裸奔了。所以先声明两个"我的"接口需认证，再放行公开浏览的 GET 通配。

#### 401/403 JSON 手动拼装

`authenticationEntryPoint` 输出 401，`accessDeniedHandler` 输出 403。注释特别说明：这发生在 Security 层（不是 MVC 层），**不经过全局异常处理器**，所以手动拼 `{"code":401,"message":"...","data":null}`，且**不依赖 Jackson ObjectMapper bean**，避免与框架初始化顺序耦合。

#### Security 层 vs MVC 层的边界

```
请求进来
  → Tomcat Servlet 容器
    → SecurityFilterChain（JwtAuthenticationFilter / UsernamePasswordAuthenticationFilter / ...）
      → 认证失败 → authenticationEntryPoint → 直接返回 401 JSON（不走全局异常处理器）
      → 授权失败 → accessDeniedHandler → 直接返回 403 JSON（不走全局异常处理器）
      → 认证通过 → DispatcherServlet → Controller
        → @PreAuthorize 鉴权失败 → AuthorizationDeniedException → GlobalExceptionHandler 捕获 → 403 Result
        → 业务异常 → BizException → GlobalExceptionHandler 捕获 → 业务错误码 Result
```

**关键区别**：
- URL 级拒绝（Filter 层）→ `authenticationEntryPoint` / `accessDeniedHandler` → 手动拼 JSON
- 方法级拒绝（MVC 层）→ `AuthorizationDeniedException` → `GlobalExceptionHandler.handleAuthorizationDenied`

### 4. FilterRegistrationBean 防二次注册

`JwtAuthenticationFilter` 是 `@Component`，Spring Boot 会自动把它注册为 Servlet 过滤器；同时它又被 `addFilterBefore` 加进了 SecurityFilterChain。如果不处理，**过滤器会执行两次**。`jwtFilterRegistration` 用 `FilterRegistrationBean.setEnabled(false)` 关闭 Boot 的自动注册，只保留 SecurityFilterChain 里这一次。

#### 为什么执行两次是灾难？

```java
// 假设过滤器执行两次：
// 第一次：解析 token → 写入 SecurityContext → 继续链路
// 第二次：再次解析同一个 token → 再次写入 SecurityContext（覆盖）
// 虽然逻辑上没问题，但：
// 1. 性能浪费（两次 Redis 查询）
// 2. 如果过滤器有副作用（如计数、日志），数据会翻倍
// 3. 某些场景下可能导致竞态条件
```

---

### 5. AuthServiceImpl：登录/注册/登出

- `register`：`@Transactional`，先查用户名唯一性（`USERNAME_ALREADY_EXISTS`），BCrypt 加密密码，insert user，再查 `role` 表找 `USER` 角色绑定 `user_role`。
- `login`：查用户 → 用户不存在或禁用统一抛 `BAD_CREDENTIALS`（防撞库，下面讲）→ `passwordEncoder.matches(raw, hashed)` 校验 → 查出用户绑定角色 → 签发 token → **写 Redis 登录态** `LOGIN_TOKEN_PREFIX + token → userId:ROLE1,ROLE2`，TTL 与 JWT 有效期一致。
- `logout`：从 request attribute 拿原始 token，删 Redis key，幂等（无 token 或重复登出都正常结束）。

#### 登录态 Redis 数据结构

```
Key: citygo:login:token:eyJhbGciOiJIUzI1NiJ9.xxx.yyy
Value: 1892345678901234567:USER,MERCHANT
TTL: 86400s（application-dev.yml：citygo.jwt.expire-seconds: 86400，即 24 小时，与 JWT 过期时间一致）
```

**为什么 value 要存角色？** 避免每个请求都查 `user_role` + `role` 两张表，实现**零查库角色加载**。

---

### 6. 登录防撞库统一错误码

`ErrorCode.BAD_CREDENTIALS(401, "用户名或密码错误")` 的注释：**不区分具体原因（用户不存在 / 密码错 / 账号禁用），防止撞库探测**。如果返回"用户名不存在"，攻击者就能用返回差异枚举出哪些用户名是注册过的。`login` 里三处失败（用户 null、status=0、密码不匹配）全部抛同一个 `BAD_CREDENTIALS`。

#### 撞库攻击原理

```
攻击者准备常用用户名字典（top1000 用户名）
  → 逐个尝试登录
  → 如果返回"用户名不存在" → 知道该用户名未注册
  → 如果返回"密码错误" → 知道该用户名已注册
  → 收集"已注册用户名列表" → 针对性爆破密码
```

**防御**：统一返回"用户名或密码错误"，攻击者无法区分是用户名错还是密码错。

---

### 7. @PreAuthorize 与 @EnableMethodSecurity

`SecurityConfig` 上 `@EnableMethodSecurity` 开启方法级授权。业务 Controller 类级标注 `@PreAuthorize("hasRole('MERCHANT')")`（如 `ShopController`、`ProductController`、`MerchantOrderController`），只有带 `ROLE_MERCHANT` 权限的用户能访问。

角色权限的映射在 `JwtAuthenticationFilter.loadAuthorities`：数据库里的角色编码 `MERCHANT` → Spring Security 权限串 `ROLE_MERCHANT`。`@PreAuthorize("hasRole('MERCHANT')")` 内部会检查 `ROLE_MERCHANT`。

#### 方法级 vs URL 级 授权对比

| 维度 | URL 级（SecurityConfig） | 方法级（@PreAuthorize） |
|------|------------------------|----------------------|
| 配置位置 | SecurityConfig.java | Controller 方法/类上 |
| 粒度 | 粗（按路径） | 细（按方法） |
| 灵活性 | 低，改配置需重启 | 高，注解即配置 |
| 表达式能力 | 弱（路径匹配） | 强（SpEL 表达式） |
| CityGo 用法 | 公开/认证接口区分 | 商家/管理员角色控制 |

坑：`@PreAuthorize` 抛出的 `AuthorizationDeniedException` 由 `GlobalExceptionHandler.handleAuthorizationDenied` 统一转 403 Result（这与 Security 层 accessDeniedHandler 是两回事——前者是方法级鉴权失败，发生在 MVC 层；后者是 URL 级拒绝，发生在过滤器链）。

## e. 面试真题

### Q1：JWT 是无状态的，你们为什么还要 Redis？

**答**：纯 JWT 签发后过期前无法主动失效——用户退出、改密、被禁用，旧 token 仍有效。CityGo 把 `token → userId:ROLE1,ROLE2` 写进 Redis（登录时顺带把角色一起缓存），登出即删 key，实现服务端可控的登录态；过滤器做"JWT 签名校验 + Redis 存在性校验"双保险，任一不满足都算未认证。JWT 解决"身份自证"，Redis 解决"可撤销"。

**加分回答**：
> "另外，Redis 里存角色列表实现了'零查库'优化——每个请求不需要再查 user_role 和 role 表。生产环境还可以扩展'多端登录管理'（一个用户多个设备登录，Redis 按用户维度存 token 集合，支持踢下线）。"

> 考官想考察：是否真的理解纯 JWT 的致命短板（无法主动失效），以及混用方案的取舍。

---

### Q2：BCrypt 为什么能防止彩虹表？为什么每次加密结果都不一样？

**答**：BCrypt 内置随机盐，每次加密把盐混进哈希结果，所以同一明文两次加密结果不同；盐让预计算的彩虹表失效。校验必须用 `matches(raw, hashed)` 而不是重新加密比对。CityGo 用 `new BCryptPasswordEncoder(10)`，强度 10 表示 2^10 轮迭代。

**为什么不能用 MD5/SHA256？**

| 算法 | 特点 | 安全性 |
|------|------|--------|
| MD5 | 快、无盐 | ❌ 已被彩虹表破解 |
| SHA256 | 快、无盐 | ❌ 可被 GPU 暴力破解 |
| BCrypt | 慢、自动加盐 | ✅ 抗彩虹表、抗暴力破解 |

**关键**：密码哈希不是加密，不需要可逆。需要的是**慢**——让暴力破解成本极高。

> 考官想考察：对"加盐慢哈希"机制的理解，以及是否知道必须用 matches 而非 encode 比对。

---

### Q3：Spring Security 的 authorizeHttpRequests 匹配顺序有什么坑？

**答**：按声明顺序匹配，第一条命中即生效。CityGo 的坑是：`GET /api/shops/my`、`GET /api/products/my` 必须放在 `GET /api/shops/**` 通配之前，否则会被通配 permitAll 误伤，导致"我的"接口裸奔。所以配置里先精确声明这两个接口 authenticated，再放行公开 GET 通配。

**类比**：就像 CSS 选择器，后面的规则不会覆盖前面的，第一条匹配就生效。

> 考官想考察：对 Security 配置顺序敏感度，以及"精确优先于通配"的原则。

---

### Q4：你们的 401 响应为什么是手动拼 JSON，不走全局异常处理器？

**答**：因为认证失败发生在 Security 过滤器链层（authenticationEntryPoint），还没进到 MVC 层，`@RestControllerAdvice` 的全局异常处理器覆盖不到。所以 SecurityConfig 里手动拼 `{"code":401,"message":"...","data":null}`，而且特意不依赖 Jackson ObjectMapper bean，避免与框架初始化顺序耦合。

**补充**：方法级鉴权失败（`@PreAuthorize`）抛出的 `AuthorizationDeniedException` 是在 MVC 层，**可以**被 `GlobalExceptionHandler` 捕获。所以 CityGo 有两套 403 处理：
1. URL 级 → Security 层 → 手动拼 JSON
2. 方法级 → MVC 层 → GlobalExceptionHandler

> 考官想考察：是否理解 Security 层与 MVC 层的边界，以及入口点/拒绝处理器的位置。

---

### Q5：FilterRegistrationBean 是干嘛的？不加会怎样？

**答**：JwtAuthenticationFilter 是 @Component，Spring Boot 会把它自动注册为 Servlet 过滤器，同时它又被 addFilterBefore 加进 SecurityFilterChain，不加处理会执行两次。FilterRegistrationBean.setEnabled(false) 关闭 Boot 自动注册，只保留 Security 链里那一次。

**执行两次的后果**：
- 性能浪费（两次 Redis 查询）
- 副作用翻倍（如计数、日志）
- 某些场景可能导致竞态条件

> 考官想考察：对 Spring Boot 自动注册机制与 Security 链重复注册问题的了解。

---

### Q6：登录失败为什么要统一返回"用户名或密码错误"？

**答**：防撞库探测。如果区分"用户不存在"和"密码错误"，攻击者可以用返回差异枚举出注册用户列表。CityGo 把用户不存在、账号禁用、密码不匹配三处失败统一抛 `BAD_CREDENTIALS(401, "用户名或密码错误")`。

**撞库攻击流程**：
```
攻击者准备常用用户名字典 → 逐个尝试登录
  → "用户名不存在" → 知道未注册
  → "密码错误" → 知道已注册
  → 收集已注册列表 → 针对性爆破
```

**防御**：统一返回，消除信息差。

> 考官想考察：安全意识，是否知道"枚举用户名"攻击面。

---

### Q7：你们怎么实现"退出登录后 token 立即失效"？

**答**：登录时把 `token → userId:roles` 写入 Redis，TTL 与 JWT 过期时间一致。登出时从 request attribute 拿到原始 token，删除对应的 Redis key。此后该 token 再来请求，JwtAuthenticationFilter 在 Redis 校验环节发现 key 不存在，视为已登出，返回 401。

**如果不做 Redis 校验**：纯 JWT 模式下，token 在过期前一直有效，即使用户点了退出，token 仍然可用（直到过期）。

> 考官想考察：对"有状态登录态管理"的理解。

---

### Q8：Spring Security 的过滤链执行顺序是什么？

**答**：
```
1. DisableEncodeUrlFilter               防 sessionId 写进 URL（6.0 新增）
2. WebAsyncManagerIntegrationFilter     异步请求的上下文传播
3. SecurityContextHolderFilter          6.0 起取代旧的 SecurityContextPersistenceFilter
4. HeaderWriterFilter                   写安全响应头（X-Frame-Options 等）
5. CsrfFilter                           （本项目已 disable）
6. LogoutFilter
7. JwtAuthenticationFilter              ★ CityGo 自定义，插在这里
8. UsernamePasswordAuthenticationFilter
9. DefaultLoginPageGeneratingFilter
10. DefaultLogoutPageGeneratingFilter
11. BasicAuthenticationFilter
12. RequestCacheAwareFilter
13. SecurityContextHolderAwareRequestFilter
14. AnonymousAuthenticationFilter       未认证时兜底给"匿名身份"
15. ExceptionTranslationFilter          捕获链尾异常 → 触发 401/403 入口点
16. AuthorizationFilter                 6.0 起取代旧的 FilterSecurityInterceptor，URL 鉴权最后一关
```

CityGo 用 `addFilterBefore(jwtAuthenticationFilter, UsernamePasswordAuthenticationFilter.class)` 把 JWT 过滤器插在用户名密码过滤器之前。

**版本提醒（面试加分）**：网上大量教程还在讲 5.x 时代的 `SecurityContextPersistenceFilter`、`FilterSecurityInterceptor`、继承 `WebSecurityConfigurerAdapter`——这三者在 Security 6.0+ 已分别被 `SecurityContextHolderFilter`、`AuthorizationFilter`、`SecurityFilterChain Bean 链式写法` 取代。面试时能主动指出"新版本过滤链变了"，比背出一份旧链更能体现真用过。

> 考官想考察：对 Security 过滤链整体结构的了解。

## f. 开发实战扩展

1. **Token 续期与多端登录**：生产用双 token（access 短 + refresh 长），access 过期用 refresh 换新；Redis 里按用户维度存 token 集合，支持"踢下线"。

2. **角色加载已零查库**：登录时把角色随登录态一起写进 Redis（`userId:ROLE1,ROLE2`），过滤器直接从 value 解析角色，请求链路不再查 user_role/role 两张表（`loadAuthorities` 仅作老格式数据的降级兜底）。生产可进一步考虑"角色变更时主动刷新缓存"，避免改角色后要等 token 过期才生效。

3. **密钥管理**：dev 的 secret 是硬编码占位，生产必须走环境变量 / KMS / Vault，且定期轮换；HS256 对称密钥泄露等于全部 token 可伪造。

4. **OAuth2/OIDC**：真实产品往往接入统一认证中心（OAuth2 + JWT），自己不做密码登录，这里只是学习项目简化。

5. **JWT  Payload 不放敏感信息**：Payload 只是 Base64Url 编码，任何人都能解码。不能放密码、手机号等敏感信息。

6. **双 Token（Access + Refresh）——生产标配**：本项目 token 有效期 86400s（24 小时）一刀切：设长了泄露风险窗口大，设短了用户频繁掉线。生产主流是双 token：
   ```
   登录 → 发 access（30分钟）+ refresh（7天）
     → access 过期 → 前端拿 refresh 静默换新 access（用户无感）
     → refresh 过期 → 才需要重新登录
     → "踢下线" = 删掉 Redis 里该用户的 refresh
   ```
   本项目省略了这层（学习取舍），但要知道这是该方案第一个该补的升级；refresh 只走换新接口、不携带业务权限，即使泄露损失也有限。

7. **Token 存哪：localStorage vs HttpOnly Cookie（XSS vs CSRF 之争）**：本项目前端（citygo-web）把 token 存 localStorage——开发方便，但**挡不住 XSS**：页面一旦被注入恶意脚本，脚本能直接 `localStorage.getItem` 读走 token。换 HttpOnly Cookie（JS 读不到）能防"偷 token"，但 Cookie 会随请求**自动携带**，要重新面对 CSRF（需配 SameSite / CSRF token）。这是一对经典矛盾，面试常问"JWT 放哪最安全"——标准答案是讲清这个 trade-off + 一切的前提是 HTTPS。本项目前端注释里也写了"生产应改 HttpOnly Cookie"。

8. **登录防爆破三板斧**：本项目登录只有"统一错误码"防撞库，还缺三层：①**验证码**（图形/滑块，拦机器流量）；②**失败锁定**（同一账号连续错 5 次锁 10 分钟，Redis INCR + EXPIRE 即可实现，与秒杀去重同款）；③**IP 限流**——可直接复用 Phase 7 的 `@RateLimit` 注解加到 `/api/auth/login` 上（本项目没加，属于一行就能补的现成强化点）。真实系统三层都要。

9. **白名单 vs 黑名单——"可撤销"的两种实现**：本项目的 Redis 登录态本质是**白名单**：token 必须在 Redis 存在才有效（每请求 1 次 Redis 查询，换来强控制：登出/封号立即生效）。另一派是**黑名单**：token 天然有效，注销时才塞进黑名单直到自然过期（平时不查 Redis、性能好，但注销后存在"尚未拉黑"窗口，且长有效期 token 会让黑名单膨胀）。CityGo 选白名单还有个顺手的理由：反正要查 Redis 拿角色列表（零查库优化），一次 GET 顺带完成存在性校验；黑名单方案反而要多查一次。

## g. 总结：面试 vs 工作的核心差异

| 维度 | 面试重点 | 工作重点 |
|------|---------|---------|
| JWT + Redis | 为什么需要 Redis（可撤销） | Redis 连接池配置、TTL 调优 |
| BCrypt | 加盐原理、为什么每次不同 | 强度参数选择（10 还是 12） |
| Security 过滤链 | 执行顺序、匹配规则 | 自定义 Filter 的性能优化 |
| 401/403 | 为什么手动拼 JSON | 统一错误格式维护 |
| 防撞库 | 统一错误码的设计 | 日志审计（记录失败 IP） |
| 方法级鉴权 | @PreAuthorize 用法 | SpEL 表达式复杂度控制 |
| 密钥管理 | HS256 对称密钥 | KMS/Vault 集成、定期轮换 |
