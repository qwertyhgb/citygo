# 05 · 商家与店铺管理

> 本篇覆盖：merchant / shop 模型、商家注册、店铺 CRUD 与营业状态、资源归属校验两级模式、@PreAuthorize MERCHANT、缓存失效与 ES 双写联动（Cache-Aside / afterCommit）。

## a. 这个模块是干嘛的

CityGo 的商家是"开店的一方"：商家注册后拥有商家身份资料（merchant 表），可以开多个店铺（shop 表），每个店铺挂商品。这一篇的核心不是 CRUD 本身，而是**资源归属校验**——商家只能操作自己的店铺，不能越权改别人的。`ShopServiceImpl` 里的 `requireMerchant` + `requireOwnedShop` 两级校验模式，是后面商品、订单、优惠券所有"归属校验"的模板。

## c. 先懂概念

1. **商家与店铺是一对多**：一个商家（merchant）可以开多个店铺（shop），店铺通过 `merchant_id` 关联商家。
2. **商家账号与用户同源**：merchant 表只存商家身份资料（名称/联系人/logo），账号本身在 user 表，靠 MERCHANT 角色区分。
3. **资源归属校验**：操作前先确认"这个资源是不是当前用户的"，不是则抛 403。CityGo 用两级：先 `requireMerchant` 确认是商家，再 `requireOwnedShop` 确认店铺属于他。
4. **营业状态独立于状态**：shop 有两个状态字段——`status`（1 正常 0 禁用，平台管控）和 `open_status`（1 营业中 0 打烊，商家自控）。
5. **@PreAuthorize 类级标注**：整个 Controller 标注 `@PreAuthorize("hasRole('MERCHANT')")`，所有方法只允许商家访问。

## d. 逐个详解

### 1. merchant / shop 模型

- `Merchant`：id、userId（`uk_user_id` 唯一，一个用户至多一个商家）、merchantName、contactName、contactPhone、logo、description、status。
- `Shop`：id、merchantId、shopName、logo、description、省市区、address、longitude/latitude（DECIMAL）、score、monthlySales、openStatus、openTime/closeTime（TIME）、notice、status。

注意 `Shop` 实体在 `merchant.entity` 包下（不是 shop 包），因为店铺归属商家域；而用户侧浏览的 `ShopBrowseService`/`ShopBrowseVO` 在 `shop` 包下，浏览侧单独建一份 VO 避免与商家侧 `ShopVO` 耦合（`ShopBrowseVO` 注释写明"任一侧字段演进互不影响"）。

### 2. 商家注册：三件事一个事务

`MerchantServiceImpl.registerMerchant`（`@Transactional`）：

1. 用户名唯一性校验（同注册）；
2. 建 user（昵称取商家名称）；
3. 查 `role` 表 `code = "MERCHANT"`，绑 `user_role`；
4. 建 merchant 资料（userId 关联）。

与普通用户注册（`AuthServiceImpl.register`）的区别只是：角色换成 MERCHANT、昵称取商家名、多一步建 merchant 表。三个写操作必须同一事务，失败整体回滚。

### 3. 资源归属校验：两级模式（核心）

`ShopServiceImpl` 两个私有方法定义了全项目的归属校验模板：

```java
private Merchant requireMerchant(Long currentUserId) {
    Merchant merchant = merchantService.getByUserId(currentUserId);
    if (merchant == null) throw new BizException(ErrorCode.MERCHANT_NOT_FOUND);
    return merchant;
}

private Shop requireOwnedShop(Long shopId, Long merchantId) {
    Shop shop = shopMapper.selectById(shopId);
    if (shop == null) throw new BizException(ErrorCode.SHOP_NOT_FOUND);
    if (!shop.getMerchantId().equals(merchantId)) throw new BizException(ErrorCode.UNAUTHORIZED_OPERATION);
    return shop;
}
```

两级语义：**不存在**返回 404（`MERCHANT_NOT_FOUND`/`SHOP_NOT_FOUND`），**存在但不属于你**返回 403（`UNAUTHORIZED_OPERATION`）。这个模式在 `ProductServiceImpl.requireOwnedProduct`、`ReviewServiceImpl.reply`、`OrderServiceImpl.requireOwnedShop` 里被反复复用——面试说"我们的越权防护统一是 404 资源不存在 + 403 越权"就来自这里。

### 4. 店铺 CRUD 与营业状态

- `create`：`requireMerchant` → 组装 Shop（默认营业中、评分 0、月销 0、正常状态）→ insert → `syncShopAfterCommit` 同步 ES。
- `update`：`requireMerchant` + `requireOwnedShop` → 按字段非空判断部分更新 → `updateById` → `syncShopAfterCommit`。方法上有 `@CacheEvict(cacheNames = "shopDetail", key = "#id")`——店铺改了，用户侧 `getDetail` 的缓存（`shopDetail::{id}`）要立即失效，下次查库回填。
- `updateOpenStatus`：切换营业状态（1 营业中 / 0 打烊），独立接口（`PATCH /{id}/open-status`）。
- `listMy`：查当前商家的全部店铺，按 id 倒序。

### 5. @PreAuthorize MERCHANT 与 currentUserId 提取

`ShopController` 类级 `@PreAuthorize("hasRole('MERCHANT')")`。每个方法通过 `currentUserId()` 从 `SecurityContextHolder` 取 `authentication.getPrincipal()` 强转 Long（过滤器认证时 principal 就是 userId），作为服务层归属校验的入参。

### 6. 缓存与 ES 联动（核心：双写一致性）

`ShopServiceImpl` 的写操作不只是改库，还要联动两个"下游"：缓存（Redis）和搜索引擎（ES）。

**（1）缓存联动：Cache-Aside 旁路缓存模式**

- 读侧：用户端 `ShopBrowseServiceImpl.getDetail` 标注 `@Cacheable(cacheNames = "shopDetail", key = "#id")`——命中缓存直接返回，未命中查库并回填。Redis key 格式为 `shopDetail::{id}`（`RedisCacheConfig` 配置 `缓存名::参数`），TTL 默认 10 分钟，JSON 序列化存储。
- 写侧：`update` 标注 `@CacheEvict(cacheNames = "shopDetail", key = "#id")`——改库后立即删除对应缓存，强制下次查询重新读库回填。

为什么"删缓存"而不是"更新缓存"？更新缓存要多查一次库计算内容，且并发写时存在旧值覆盖新值的竞态；删除则让下次读自然回填最新数据，简单且天然并发安全——这是 Cache-Aside 模式的标准做法。

**（2）ES 联动：事务提交后同步**

`syncShopAfterCommit` 用 `searchSync.afterCommit(() -> shopSearchService.syncShop(...))` 在事务提交后同步 ES（详见 14 篇）。注意回调里是重新 `selectById` 而非复用内存对象——为了拿到数据库回填的 `create_time`、`review_count` 等完整字段，保证 ES 文档与库一致。

**（3）空方法删缓存技巧**

评价改评分也会影响 `shopDetail` 缓存（缓存里含 score），但 `ReviewServiceImpl` 不方便直接标 `@CacheEvict`（key 参数名不同、语义上它操作的是评价）。解法：`ShopBrowseServiceImpl.evictDetailCache(Long shopId)` 是一个**方法体为空的公开方法，仅靠方法上的 `@CacheEvict` 生效**，其他 Service 调用它即可完成失效——把"删缓存"封装成语义化接口。

**（4）AOP 代理的坑**

`@CacheEvict`/`@Transactional` 都基于 AOP 代理实现，**同类内部 `this.update(...)` 调用会绕过代理导致注解失效**。必须从外部经 Spring 代理对象调用（如 Controller 注入接口调用）。这是判断"用注解还是手写 `cacheManager.getCache(...).evict(...)`"的主要依据：外部调用用注解，同类内部或批量/条件复杂场景手写。

## e. 面试真题

**Q1：商家和店铺是什么关系？为什么不用一张表？**

答：一对多关系——一个商家可开多个店铺。分成两张表：merchant 存商家平台身份（名称/联系人/资质），shop 存具体店铺（位置/营业时间/评分）。如果合成一张表，多店铺会导致商家资料重复冗余，且后续"商家总部 + 分店"的层级关系无法表达。

> 考官想考察：对实体关系建模的判断，以及"身份"与"经营实体"的分离。

**Q2：你们的越权防护是怎么做的？**

答：统一用"归属校验"两级模式：先 `requireMerchant` 确认当前用户是商家，再 `requireOwnedShop` 确认资源属于该商家。语义上"资源不存在"返回 404、"存在但不属于你"返回 403。这套模式在商品、订单、评价、优惠券里复用，保证所有写操作都做归属校验。

> 考官想考察：是否把"越权防护"落到具体代码模式，而非空谈"要做权限校验"。

**Q3：shop 为什么有 status 和 open_status 两个状态字段？**

答：职责不同。`status` 是平台管控（1 正常 0 禁用，平台封店用），`open_status` 是商家自控（1 营业中 0 打烊，商家自己开关店）。两个维度正交，商家能自己打烊但不能自己解除平台封禁。

> 考官想考察：对"状态字段职责单一"的理解，避免一个字段塞多种语义。

**Q4：@PreAuthorize("hasRole('MERCHANT')") 是怎么生效的？**

答：SecurityConfig 上 `@EnableMethodSecurity` 开启方法级授权；JwtAuthenticationFilter 认证时把用户角色加载为 `ROLE_MERCHANT` 权限写入 Authentication；`@PreAuthorize` 在方法调用前检查当前 Authentication 是否含该角色，不含抛 `AuthorizationDeniedException`，由 GlobalExceptionHandler 统一转 403 Result。

> 考官想考察：对 Spring Security 方法级授权的完整链路理解。

**Q5：商家注册为什么要放在一个事务里？**

答：注册 = 建 user + 绑 MERCHANT 角色 + 建 merchant 资料，三步必须原子。任一失败都该整体回滚，否则会出现"有账号没商家资料"或"有商家资料没角色"的脏数据。`@Transactional(rollbackFor = Exception.class)` 保证原子性。

> 考官想考察：对多步写操作事务边界的判断。

**Q6：更新店铺后为什么要失效缓存？**

答：用户侧店铺详情接口 `getDetail` 用了 `@Cacheable("shopDetail", key = "#id")`，店铺信息修改后缓存里的旧数据不失效，用户会读到旧店铺名/地址。所以 `update` 方法上配 `@CacheEvict(cacheNames = "shopDetail", key = "#id")`，写后立即失效，下次访问重新查库回填，保证一致性。

> 考官想考察：对"写操作与缓存一致性"的联动意识。

**Q7：为什么用 @CacheEvict 注解而不是在方法里手写删缓存代码？**

答：功能上等价，但注解有四个优势：① 业务零侵入，缓存是横切关注点，声明在方法签名上一眼可见；② 防遗漏，多处写操作都需要失效同一缓存时，手写靠人记容易漏，注解便于 review；③ 换缓存实现（Redis → Caffeine）只改配置不改业务代码；④ 与 @Transactional 一样是声明式编程思想。但注解有限制：基于 AOP 代理，同类内部 this 调用会绕过代理失效，且批量/复杂条件删除表达不了——这些场景才切回手写 `cacheManager.getCache(...).evict(...)`。

> 考官想考察：对声明式 vs 编程式的权衡，以及 AOP 代理失效场景的了解。

**Q8：@CacheEvict 的执行时机和方法事务有什么关系？**

答：`@CacheEvict` 默认在方法成功返回后（after invocation）执行删除；缓存注解和事务注解叠加时都要注意经过代理。本项目 update 同时有 `@Transactional` 和 `@CacheEvict`，ES 同步则额外通过 `SearchSync.afterCommit` 注册事务同步回调，确保"MySQL 提交成功 → 才写 ES"，事务回滚不会产生 ES 幽灵文档。

> 考官想考察：注解叠加时的执行顺序意识，以及缓存/ES 与事务的一致性设计。

## f. 开发实战扩展

1. **商家入驻审核流**：真实平台商家注册要过资质审核（营业执照、食品经营许可），merchant 表加 `audit_status` 字段 + 审核流程，而不是注册即生效。
2. **商家后台独立服务**：生产里商家端和用户端会拆成不同服务/网关路由，而非一个 Controller 混在一起。
3. **地理位置索引**：shop 的经纬度生产会用 MySQL 空间索引或 ES geo_point 做"附近店铺"（本项目 ES 已支持，见 14 篇），纯 DECIMAL 只能精确匹配不能范围检索。
4. **营业时间时区**：open_time/close_time 用 TIME 类型不带时区，跨时区门店要存带时区的时间或统一 UTC。
