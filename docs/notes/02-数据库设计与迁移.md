# 02 · 数据库设计与迁移

> 本篇覆盖：14 张表的设计决策（无物理外键 / 雪花 ID / 软删除 / 快照 / 冗余销量 / 状态枚举区间化 / DECIMAL）、索引设计思路、V1-V5 迁移脚本细节（INSERT IGNORE、相对时间种子数据、ALTER 加字段）、Flyway 工作流（已发布迁移不可改）。

## a. 这个模块是干嘛的

CityGo 的数据库是整条业务链路的"唯一事实源"：用户、角色、商家、店铺、商品、分类、订单、支付、优惠券、评价、地址，共 14 张表。这一篇讲的是"表怎么设计、为什么这么设计、结构变更怎么管"。面试里被问"为什么不用物理外键""为什么主键不用自增""软删除怎么实现"，答案全来自这套设计和 `database-design.md` 里的决策记录。

## c. 先懂概念

1. **物理外键 vs 逻辑外键**：物理外键是数据库层的 `FOREIGN KEY` 约束；逻辑外键是"业务字段 + 索引"表达关联关系，一致性靠应用层保证。
2. **雪花 ID**：MyBatis-Plus 的 `IdType.ASSIGN_ID` 生成的 64 位趋势递增 ID，全局唯一、不依赖数据库自增。
3. **软删除**：不物理删除行，而是把 `deleted` 字段置 1，配合 MyBatis-Plus 全局逻辑删除配置自动过滤。
4. **快照**：订单明细、收货信息把下单那一刻的数据固化进订单表，防止商品改价/地址修改导致历史订单失真。
5. **冗余字段**：把"需要频繁累加/展示"的销量（`sales`/`monthly_sales`）单独存一列，避免每次 `COUNT` 明细。
6. **Flyway 已发布迁移不可改**：迁移脚本一旦在某个环境执行过，就会记进 `flyway_schema_history`，改旧脚本会导致校验和（checksum）不匹配，启动直接报错。

### 2. 设计决策：为什么不用物理外键

`database-design.md` 决策记录第 1 条：物理外键会在删除/更新主体时强校验关联，导致高耦合、加锁范围大、迁移与分片困难。企业实践普遍用"逻辑外键（业务字段）+ 索引"代替，靠应用层保证一致性。

这解释了为什么 V1 的 DDL 里**一个 FOREIGN KEY 都没有**，但跨表关系字段（如 `merchant.user_id`、`shop.merchant_id`）都建了索引。代价是完整性要靠代码保证，比如 `ShopServiceImpl.requireOwnedShop` 的归属校验，和数据库层面 `uk_*` 唯一索引兜底。

### 3. 为什么主键用雪花 ID 不用自增

决策记录第 2 条：自增 ID 在分布式多实例写入时会产生冲突，且易被遍历猜透（`/api/orders/1001`、`1002` 挨个猜）。雪花 ID 全局唯一、趋势递增、无需额外依赖。

代码里的落地方式：每个实体的 `id` 字段都标注 `@TableId(type = IdType.ASSIGN_ID)`（如 `User`、`Product`、`Orders`），由 MyBatis-Plus 在 insert 时生成雪花 ID。业务订单号 `order_no` 则用 `IdWorker.getIdStr()` 单独生成字符串雪花号，对外展示用。

### 4. 软删除怎么做

决策记录第 3 条：一笔订单/用户被误删可恢复，审计可追溯。实现是每张表末尾三个公共字段之一 `deleted TINYINT NOT NULL DEFAULT 0`。

关键是 MyBatis-Plus 的全局配置（`application.yml`）：

```yaml
mybatis-plus:
  global-config:
    db-config:
      logic-delete-field: deleted
      logic-delete-value: 1
      logic-not-delete-value: 0
```

配置后，MP 的 `selectById`/`selectList` 会自动拼 `deleted=0`，`deleteById` 会变成 `UPDATE ... SET deleted=1`，业务代码无感。坑在 13/15 篇会讲：**自定义 `@Select`/`@Update` SQL 不走 MP 逻辑删除自动注入**，必须手动加 `deleted=0`（参考 `ReviewMapper.avgRatingByShop`）。

### 5. 快照与冗余销量的取舍

- **快照**（决策第 4 条）：`order_item` 存 `product_name`/`product_image`/`price` 快照，`orders` 存 `receiver_*` 收货快照。原因是商品会改价、下架、删除，地址会被修改，历史订单必须永远正确展示。代码里 `OrderServiceImpl.create` 的 e/f 步就是把这些字段从 `product`/`address` 拷贝进订单。
- **冗余销量**（决策第 8 条）：`shop.monthly_sales` 和 `product.sales` 是冗余字段，下单时 `UPDATE` 累加（`ShopMapper.addMonthlySales`、`ProductMapper.deductStock` 里的 `sales = sales + ?`），而不是每次 `COUNT` 明细。代价是需在事务内与明细保持一致。

### 6. 状态枚举区间化

决策第 7 条：订单状态按业务推进顺序离散取值 `10 待支付 / 20 已支付 / 30 已接单 / 40 配送中 / 50 已完成 / 60 已取消 / 70 退款中 / 80 已退款`。为什么不是 1、2、3 连续小整数：预留中间态与扩展空间，数值区间化让状态可比较（如 `status >= 20` 表示已支付）。枚举类 `OrderStatus` 完整承载了这套编码和状态机流转表。

### 7. 金额与坐标用 DECIMAL

决策第 6 条：`DECIMAL(10,2)` 是精确定点数，避免浮点精度误差（`0.30000000000000004`）。评分 `DECIMAL(2,1)`、经纬度 `DECIMAL(10,6)` 同理。代码里所有金额字段都是 `BigDecimal`（`Orders.totalAmount`、`Product.price`），运算用 `multiply`/`add`/`subtract`，从不碰 `double`。

### 8. 索引设计思路

索引不是越多越好，每一张表都是按查询场景建的：

- `shop.idx_city_district(city, district)`：商圈首页按城市/区筛选，最左前缀命中 `city`；
- `product.idx_shop_status(shop_id, status)`：店铺内只查上架商品（`WHERE shop_id=? AND status=1` 一次命中）；
- `orders.idx_user_status(user_id, status)`：我的订单按状态过滤；
- `user_coupon.idx_user_status(user_id, status)`：我的可用/已用/过期券。

### 9. V1-V5 迁移脚本逐一看

- **V1**：全部 14 张表 DDL。通用约定写在文件头注释：InnoDB、utf8mb4、utf8mb4_unicode_ci、主键 BIGINT 不用自增、每表三个公共字段、不用物理外键。
- **V2**：`INSERT IGNORE INTO role` 插入三条角色，`IGNORE` 配合 `uk_code` 保证脚本可重复执行不冲突。固定 `id=1,2,3`。
- **V3**：`INSERT IGNORE` 插入 6 个一级分类（火锅/烧烤/奶茶/快餐/甜品/小吃），`parent_id=0`、`sort 1-6`。
- **V4**：2 张平台券。重点在**相对时间**：`valid_start` 用 `DATE_SUB(NOW(), INTERVAL 1 DAY)`，`valid_end` 用 `DATE_ADD(NOW(), INTERVAL 1 YEAR)`，让这两张券"永远可用"，避免迁移执行时刻固化导致后启动的实例拿到过期券。
- **V5**：`ALTER TABLE product ADD COLUMN` 加 4 个秒杀字段（`seckill_price`/`seckill_stock`/`seckill_start`/`seckill_end`），`ALTER TABLE orders ADD COLUMN source`。这是"新增字段"用 ALTER 而非改 V1 的标准示范——**已发布的迁移不可改，只能新增迁移**。

### 10. Flyway 工作流

- 启动时按版本号顺序执行 `classpath:db/migration` 下未执行的脚本；
- 每个已执行脚本记录到 `flyway_schema_history`（含 checksum）；
- **已发布迁移不可改**：改了 V1 的 SQL，checksum 变化，Flyway 校验失败拒绝启动。正确做法是新增 V6 迁移；
- 版本号命名 `V{n}__{描述}.sql`（双下划线），`{n}` 递增。

坑：开发期手滑改了已提交的迁移脚本，会看到 `Migration checksum mismatch` 报错。学习项目可以 `flyway clean`（会清库，危险），生产只能通过新增迁移修补。

## e. 面试真题

**Q1：为什么不建物理外键？**

答：物理外键在删除/更新主体时强校验关联，导致表间高耦合、加锁范围大、分库分表与迁移困难。CityGo 用"逻辑外键（业务字段）+ 索引"表达关系，一致性靠应用层（服务层归属校验）和唯一索引兜底。代价是完整性要代码保证，所以服务层有大量 `requireOwned*` 这类校验方法。

> 考官想考察：是否理解"约束放在 DB 还是应用层"的工程权衡，而非只会背"外键保证一致性"。

**Q2：主键为什么用雪花 ID？雪花 ID 有什么缺点？**

答：自增 ID 在分布式多实例写入会冲突、且可被遍历猜透。雪花 ID 全局唯一、趋势递增、不依赖 DB 自增，契合分库分表和 MP 默认策略。缺点是：依赖机器时钟（时钟回拨会产生重复）、64 位较长、不具备业务含义（不像订单号可读）。CityGo 用 `@TableId(type = IdType.ASSIGN_ID)` 生成主键，业务订单号 `order_no` 单独用 `IdWorker.getIdStr()` 生成字符串雪花号。

> 考官想考察：是否知道雪花 ID 的适用场景和时钟回拨这个经典缺陷。

**Q3：软删除是怎么实现的？有什么坑？**

答：每表带 `deleted` 字段，MyBatis-Plus 全局配置 `logic-delete-field: deleted`、`logic-delete-value: 1`、`logic-not-delete-value: 0`，之后 `selectById` 自动拼 `deleted=0`，`deleteById` 变 `UPDATE deleted=1`。最大的坑是：**自定义 `@Select`/`@Update` SQL 不走逻辑删除自动注入**，必须手动加 `deleted=0`（如 `ReviewMapper.avgRatingByShop`）；另外唯一索引与软删除会冲突——软删后唯一键仍占用，反复创建会撞唯一索引，生产通常用"唯一键 + deleted"组合或租户隔离解决。

> 考官想考察：是否真实现过软删除，且知道它与唯一索引、手写 SQL 的冲突。

**Q4：订单明细为什么要做快照？**

答：商品会改价、下架甚至删除，收货地址会被修改。快照把下单那一刻的商品名/单价/收货信息固化进 `order_item` 和 `orders`，保证历史订单永远正确展示，符合交易一致性要求。CityGo 在 `OrderServiceImpl.create` 的 e/f 步把 `product` 和 `address` 的字段拷贝进订单。

> 考官想考察：对电商交易数据一致性的理解，以及"历史数据不可变"的意识。

**Q5：shop.monthly_sales 这种冗余字段为什么划算？**

答：销量在列表页高频展示且频繁累加，冗余为单列后下单只需 `UPDATE monthly_sales = monthly_sales + ?`，避免每次 `COUNT` 订单明细，显著降低热点读写压力。代价是要在事务内保证与明细一致。CityGo 用 `ShopMapper.addMonthlySales` 实现，下单加、取消减。

> 考官想考察：是否理解"空间换时间 / 避免聚合查询"的冗余设计思想。

**Q6：为什么金额要用 DECIMAL 而不是 DOUBLE？**

答：DOUBLE 是二进制浮点，存在精度误差（如 0.1 + 0.2 != 0.3），金额累计/对账会出现 0.30000000000000004 这类问题。DECIMAL 是精确定点数，`DECIMAL(10,2)` 保证两位小数精确。CityGo 所有金额字段都是 `BigDecimal`，运算只用 `multiply/add/subtract`，折扣用 `divide(100, 2, RoundingMode.HALF_UP)` 显式指定舍入。

> 考官想考察：对浮点精度陷阱和金融级计算规范的敏感度。

**Q7：Flyway 已发布的迁移脚本能改吗？为什么？**

答：不能。迁移脚本执行后记入 `flyway_schema_history` 并保存 checksum，改旧脚本会导致 checksum 不匹配，Flyway 校验失败拒绝启动。正确做法是新增 V6 迁移。CityGo 的 V5 秒杀字段就是新增迁移（ALTER 加字段）而非改 V1。

> 考官想考察：对数据库迁移工作流"不可变、可追溯"原则的理解。

## f. 开发实战扩展

1. **唯一键与软删除冲突**：生产里 `uk_username` 这种唯一索引在软删除后会占用，重复创建同名用户撞唯一键。方案：唯一索引加 `deleted` 列（`uk(username, deleted)`），或软删时把 username 改成 `username_deleted_{id}`。
2. **大表分库分表**：雪花 ID 已经为分片做好准备；`orders` 这类大表生产会按 `user_id` 分片，`order_no` 做全局路由索引。
3. **迁移脚本纳入 CI**：生产把 Flyway 迁移接入 CI/CD，上线前先在 staging 跑一遍迁移并做 checksum 校验，防止线上结构漂移。
4. **在线 DDL**：MySQL 8 的 `ALTER` 默认 INPLACE，但对大表加字段仍要评估锁表风险，生产用 gh-ost / pt-osc 这类在线变更工具。
