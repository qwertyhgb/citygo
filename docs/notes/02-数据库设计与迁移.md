## c. 先懂概念

1. **物理外键 vs 逻辑外键**：物理外键是数据库层的 `FOREIGN KEY` 约束；逻辑外键是"业务字段 + 索引"表达关联关系，一致性靠应用层保证。
2. **雪花 ID**：MyBatis-Plus 的 `IdType.ASSIGN_ID` 生成的 64 位趋势递增 ID，全局唯一、不依赖数据库自增。
3. **软删除**：不物理删除行，而是把 `deleted` 字段置 1，配合 MyBatis-Plus 全局逻辑删除配置自动过滤。
4. **快照**：订单明细、收货信息把下单那一刻的数据固化进订单表，防止商品改价/地址修改导致历史订单失真。
5. **冗余字段**：把"需要频繁累加/展示"的销量（`sales`/`monthly_sales`）与评价总数（`review_count`）单独存一列，避免每次 `COUNT` 明细。
6. **Flyway 已发布迁移不可改**：迁移脚本一旦在某个环境执行过，就会记进 `flyway_schema_history`，改旧脚本会导致校验和（checksum）不匹配，启动直接报错。

### 2. 设计决策：为什么不用物理外键

`database-design.md` 决策记录第 1 条：物理外键会在删除/更新主体时强校验关联，导致高耦合、加锁范围大、迁移与分片困难。企业实践普遍用"逻辑外键（业务字段）+ 索引"代替，靠应用层保证一致性。

这解释了为什么 V1 的 DDL 里**一个 FOREIGN KEY 都没有**，但跨表关系字段（如 `merchant.user_id`、`shop.merchant_id`）都建了索引。代价是完整性要靠代码保证，比如 `ShopServiceImpl.requireOwnedShop` 的归属校验，和数据库层面 `uk_*` 唯一索引兜底。

#### 物理外键 vs 逻辑外键 详细对比

| 维度 | 物理外键 | 逻辑外键 |
|------|---------|---------|
| **定义位置** | 数据库 DDL 中 `FOREIGN KEY` 约束 | 仅字段命名 + 索引，代码层面约定 |
| **数据一致性** | 数据库**自动强制**（级联更新/删除） | 依赖**业务代码**保证 |
| **写入性能** | 每次写入需检查引用，有额外开销 | 无额外检查，写入更快 |
| **并发性能** | 外键检查会加锁，高并发下可能成为瓶颈 | 无锁竞争，更适合高并发 |
| **分库分表** | 跨库/跨分片无法建立外键 | 天然支持分布式场景 |
| **数据迁移/归档** | 必须按依赖顺序清理 | 灵活处理，无依赖顺序限制 |
| **批量操作** | 大批量导入/删除时外键检查拖慢速度 | 批量操作效率高 |
| **代码可读性** | 数据库自文档化 | 需看注释或文档，或从代码推断 |
| **误操作防护** | 数据库阻止非法关联数据写入 | 代码 bug 可能导致脏数据 |

#### 什么时候用物理外键？

| 场景 | 原因 |
|------|------|
| 小型项目/内部工具 | 数据量小，性能不敏感，追求开发效率 |
| 强一致性要求极高 | 金融级对账场景，不允许任何脏数据 |
| 多应用共用一个数据库 | 不同应用直接操作 DB，无法统一走代码校验 |
| 团队数据库能力强于代码能力 | 靠 DBA 管理约束比靠程序员更可靠 |

### 3. 为什么主键用雪花 ID 不用自增

决策记录第 2 条：自增 ID 在分布式多实例写入时会产生冲突，且易被遍历猜透（`/api/orders/1001`、`1002` 挨个猜）。雪花 ID 全局唯一、趋势递增、无需额外依赖。

代码里的落地方式：每个实体的 `id` 字段都标注 `@TableId(type = IdType.ASSIGN_ID)`（如 `User`、`Product`、`Orders`），由 MyBatis-Plus 在 insert 时生成雪花 ID。业务订单号 `order_no` 则用 `IdWorker.getIdStr()` 单独生成字符串雪花号，对外展示用。

#### 分布式 ID 方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|---------|
| 自增 ID | 简单、有序、存储小 | 分布式冲突、不安全（可遍历）、依赖数据库 | 单库单表 |
| 雪花 ID | 全局唯一、趋势递增、不依赖 DB、生成快 | 依赖时钟（回拨会重复）、64 位较长、前端精度丢失 | 高并发分布式（**CityGo 选用**） |
| UUID | 全局唯一、无依赖 | 无序、存储大（36 字符）、索引性能差 | 低并发、无排序需求 |
| 美团 Leaf | 高可用、可监控、号段模式 | 需额外部署服务 | 大厂生产环境 |
| 百度 UidGenerator | 缓存预生成、性能好 | 引入额外依赖 | 高并发生产环境 |

#### 真实工作踩坑：前端精度丢失

JavaScript 的 `Number` 类型最大安全整数是 `2^53-1`（约 9e15），雪花 ID 是 64 位。前端接收时会丢失精度！

**解决方案**：
```java
// 方案 1：序列化时转字符串
@JsonFormat(shape = JsonFormat.Shape.STRING)
private Long id;

// 方案 2：全局配置（WebMvcConfigurer）
@Override
public void configureMessageConverters(List<HttpMessageConverter<?>> converters) {
    // 让 Jackson 把 Long 序列化为 String
}
```

### 4. 软删除怎么做

决策记录第 3 条：一笔订单/用户被误删可恢复，审计可追溯。实现是每张表末尾三个公共字段之一 `deleted TINYINT NOT NULL DEFAULT 0`。

关键是 MyBatis-Plus 的全局配置（`application.yml`）：

```yaml
mybatis-plus:
  global-config:
    db-config:
      logic-delete-field: deleted
      logic-delete-value: 1
      logic-not-delete-value: 0
```

配置后，MP 的 `selectById`/`selectList` 会自动拼 `deleted=0`，`deleteById` 会变成 `UPDATE ... SET deleted=1`，业务代码无感。

#### 坑 1：自定义 SQL 不走逻辑删除自动注入（最严重）

```java
// ReviewMapper.java — 必须手动加 deleted = 0！
@Select("SELECT AVG(rating) FROM review WHERE shop_id = #{shopId} AND status = 1 AND deleted = 0")
BigDecimal avgRatingByShop(@Param("shopId") Long shopId);
```

如果漏了 `AND deleted = 0`，已删除的评价会被统计进去，店铺评分就不准了！

#### 坑 2：唯一索引 + 软删除冲突

```sql
-- 用户表有 uk_username
-- 用户 A 注册 "zhangsan"，然后被软删
-- 新用户 B 想注册 "zhangsan" → 唯一索引冲突！
```

**生产解决方案对比**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| `uk(username, deleted)` | 简单 | 只能有一个 deleted=0 的记录 |
| 软删时改 username | 彻底释放唯一键 | 需要改业务代码 |
| 逻辑删除改物理删除 | 无冲突 | 丢失审计能力 |

**CityGo 推荐做法**：软删时把 username 改成 `username_deleted_{id}`。

#### 坑 3：关联查询漏过滤

```sql
-- 错误：只过滤了主表，没过滤关联表
SELECT o.*, u.username 
FROM orders o 
JOIN user u ON o.user_id = u.id 
WHERE o.deleted = 0
-- 漏了：AND u.deleted = 0
```

### 5. 快照与冗余销量的取舍

#### 快照设计

**为什么订单要做快照？** 商品会改价、下架、删除，收货地址会被修改。历史订单必须**永远正确展示**下单时的信息。

| 字段 | 是否快照 | 原因 |
|------|---------|------|
| 收货人姓名/电话/地址 | ✅ 快照 | 用户会修改 |
| 商品名称/图片/价格 | ✅ 快照 | 商家会修改 |
| 店铺名称 | ❌ 通常不快照 | 变化频率低，且可接受展示最新名称 |
| 用户昵称 | ❌ 不快照 | 非交易关键信息 |

**性能注意**：快照字段不要太多，否则订单表膨胀。非关键信息（如用户头像）可以用 ID 关联，展示时查最新。

#### 冗余销量设计

`shop.monthly_sales` 和 `product.sales` 是冗余字段，下单时 `UPDATE` 累加，而不是每次 `COUNT` 明细。

**为什么冗余？** 销量在列表页高频展示且频繁累加，冗余为单列后下单只需原子更新，避免每次 `COUNT` 订单明细，显著降低热点读写压力。

**代价**：需在事务内保证与明细一致。下单时累加，取消时回减。

#### ❌ 常见错误：先查再写的销量更新（并发问题）

```java
// 错误！两个线程同时读到 100，都加 1 后写回 101
int sales = shopMapper.selectById(shopId).getMonthlySales();
shop.setMonthlySales(sales + quantity);
shopMapper.updateById(shop);
```

#### ✅ 正确做法：数据库原子表达式

```java
// ShopMapper.java
@Update("UPDATE shop SET monthly_sales = monthly_sales + #{delta} WHERE id = #{id}")
int addMonthlySales(@Param("id") Long id, @Param("delta") int delta);

// ProductMapper.java
@Update("UPDATE product SET stock = stock - #{quantity}, sales = sales + #{quantity} " +
        "WHERE id = #{id} AND stock >= #{quantity}")
int deductStock(@Param("id") Long id, @Param("quantity") int quantity);
```

**核心原理**：`UPDATE ... SET sales = sales + ?` 是单条原子语句，数据库行锁保证同一时刻只有一个请求能修改成功。返回 0 影响行数即库存不足（CAS 思想）。

### 6. 状态枚举区间化

决策第 7 条：订单状态按业务推进顺序离散取值 `10 待支付 / 20 已支付 / 30 已接单 / 40 配送中 / 50 已完成 / 60 已取消 / 70 退款中 / 80 已退款`。

**为什么不是 1、2、3 连续小整数？**
1. **预留扩展空间**：比如未来在 10 和 20 之间加"待确认"状态
2. **数值区间化让状态可比较**：`status >= 20` 表示"已支付及之后的状态"

**状态机流转**：
```
10 待支付 --支付--> 20 已支付 --接单--> 30 已接单 --配送--> 40 配送中 --完成--> 50 已完成
10 待支付 --取消--> 60 已取消
20..40 --退款--> 70 退款中 --退款成功--> 80 已退款   （本期不实现流转）
```

**并发安全的状态流转（CAS 思想）**：
```java
// 商家接单 — 只有 status=20（已支付）的订单才能被接单
int updated = ordersMapper.updateStatus(orderId, OrderStatus.ACCEPTED.getCode(), OrderStatus.PAID.getCode());
if (updated == 0) {
    throw new BizException(ErrorCode.CONFLICT, "订单状态已变更，请刷新后重试");
}
```

对应的 SQL：
```sql
UPDATE orders SET status = 30 WHERE id = ? AND status = 20
```

### 7. 金额与坐标用 DECIMAL

决策第 6 条：`DECIMAL(10,2)` 是精确定点数，避免浮点精度误差（`0.30000000000000004`）。评分 `DECIMAL(2,1)`、经纬度 `DECIMAL(10,6)` 同理。

代码里所有金额字段都是 `BigDecimal`，运算只用 `multiply`/`add`/`subtract`，从不碰 `double`。

#### ❌ 绝对不能做的事

```java
// 错误：用 double 构造 BigDecimal
new BigDecimal(0.1);  // 0.1000000000000000055511151231257827021181583404541015625

// 正确：用字符串构造
new BigDecimal("0.1");  // 精确的 0.1
```

#### ✅ 正确的金额计算

```java
// 计算折扣价：原价 * 折扣率 / 100
BigDecimal discountPrice = originalPrice
    .multiply(new BigDecimal(discountRate))
    .divide(new BigDecimal(100), 2, RoundingMode.HALF_UP);  // 保留2位，四舍五入

// 实付金额 = 商品总额 - 优惠金额
BigDecimal payAmount = totalAmount.subtract(discountAmount);
```

### 8. 索引设计思路

索引不是越多越好，每一张表都是按**查询场景**建的：

- `shop.idx_city_district(city, district)`：商圈首页按城市/区筛选，最左前缀命中 `city`；
- `product.idx_shop_status(shop_id, status)`：店铺内只查上架商品（`WHERE shop_id=? AND status=1` 一次命中）；
- `orders.idx_user_status(user_id, status)`：我的订单按状态过滤；
- `user_coupon.idx_user_status(user_id, status)`：我的可用/已用/过期券。

#### 索引失效的常见情况

```sql
-- 1. 隐式类型转换（status 是 TINYINT，传字符串）
WHERE shop_id = 100 AND status = '1'   -- 可能失效

-- 2. OR 导致索引失效
WHERE shop_id = 100 OR status = 1       -- 可能走全表

-- 3. 函数操作
WHERE YEAR(create_time) = 2024          -- 索引失效

-- 4. 前导模糊查询
WHERE username LIKE '%zhang%'           -- 索引失效
```

### 9. V1-V6 迁移脚本逐一看

- **V1**：全部 14 张表 DDL。通用约定写在文件头注释：InnoDB、utf8mb4、utf8mb4_unicode_ci、主键 BIGINT 不用自增、每表三个公共字段、不用物理外键。
- **V2**：`INSERT IGNORE INTO role` 插入三条角色，`IGNORE` 配合 `uk_code` 保证脚本可重复执行不冲突。固定 `id=1,2,3`。
- **V3**：`INSERT IGNORE` 插入 6 个一级分类（火锅/烧烤/奶茶/快餐/甜品/小吃），`parent_id=0`、`sort 1-6`。
- **V4**：2 张平台券。重点在**相对时间**：`valid_start` 用 `DATE_SUB(NOW(), INTERVAL 1 DAY)`，`valid_end` 用 `DATE_ADD(NOW(), INTERVAL 1 YEAR)`，让这两张券"永远可用"，避免迁移执行时刻固化导致后启动的实例拿到过期券。
- **V5**：`ALTER TABLE product ADD COLUMN` 加 4 个秒杀字段（`seckill_price`/`seckill_stock`/`seckill_start`/`seckill_end`），`ALTER TABLE orders ADD COLUMN source`。这是"新增字段"用 ALTER 而非改 V1 的标准示范——**已发布的迁移不可改，只能新增迁移**。
- **V6**：`ALTER TABLE user_coupon DROP INDEX uk_user_coupon, ADD INDEX idx_user_coupon` 改造领券索引以支持 `per_user_limit > 1` 多张领券（防重改由 Redis 锁与业务控制）；`ALTER TABLE shop ADD COLUMN review_count INT NOT NULL DEFAULT 0` 增加评价数冗余字段。

### 10. Flyway 工作流

- 启动时按版本号顺序执行 `classpath:db/migration` 下未执行的脚本；
- 每个已执行脚本记录到 `flyway_schema_history`（含 checksum）；
- **已发布迁移不可改**：改了 V1 的 SQL，checksum 变化，Flyway 校验失败拒绝启动。正确做法是新增 V6/V7 迁移；
- 版本号命名 `V{n}__{描述}.sql`（双下划线），`{n}` 递增。

坑：开发期手滑改了已提交的迁移脚本，会看到 `Migration checksum mismatch` 报错。学习项目可以 `flyway clean`（会清库，危险），生产只能通过新增迁移修补。

#### 团队协作规范

1. **版本号分配**：开发前在群里/文档中认领版本号，避免冲突
2. **脚本审查**：迁移脚本纳入 Code Review，重点检查：
   - 是否修改了已发布的脚本？
   - 大表 ALTER 是否有锁表风险？
   - 种子数据是否幂等（`INSERT IGNORE`/`IF NOT EXISTS`）？
3. **CI/CD 集成**：staging 环境自动执行迁移，checksum 校验通过才能上线
4. **回滚预案**：生产迁移失败时，准备 `V{n+1}__rollback_xxx.sql` 补偿脚本

## e. 面试真题

### Q1：为什么不建物理外键？

**答**：物理外键在删除/更新主体时强校验关联，导致表间高耦合、加锁范围大、分库分表与迁移困难。CityGo 用"逻辑外键（业务字段）+ 索引"表达关系，一致性靠应用层（服务层归属校验）和唯一索引兜底。代价是完整性要代码保证，所以服务层有大量 `requireOwned*` 这类校验方法。

**加分回答**：
> "不过物理外键也不是一无是处。如果多团队共用一个数据库、或者金融级强一致性场景，物理外键 + 应用层双重保障更稳妥。我们项目因为是单体应用、团队统一，所以用逻辑外键更灵活。"

> 考官想考察：是否理解"约束放在 DB 还是应用层"的工程权衡，而非只会背"外键保证一致性"。

---

### Q2：主键为什么用雪花 ID？雪花 ID 有什么缺点？

**答**：自增 ID 在分布式多实例写入会冲突、且可被遍历猜透。雪花 ID 全局唯一、趋势递增、不依赖 DB 自增，契合分库分表和 MP 默认策略。

**缺点**：
1. **依赖机器时钟**（时钟回拨会产生重复）—— 解决方案：等待策略、序列号扩展、UidGenerator/Leaf
2. **64 位较长** —— 存储比自增 ID 大
3. **前端精度丢失** —— JavaScript Number 最大安全整数 2^53-1，雪花 ID 超出会精度丢失。解决方案：`@JsonFormat(shape = JsonFormat.Shape.STRING)` 序列化为字符串
4. **不具备业务含义** —— 不像订单号可读

CityGo 用 `@TableId(type = IdType.ASSIGN_ID)` 生成主键，业务订单号 `order_no` 单独用 `IdWorker.getIdStr()` 生成字符串雪花号。

> 考官想考察：是否知道雪花 ID 的适用场景和时钟回拨这个经典缺陷，以及前端精度丢失这个实战坑。

---

### Q3：软删除是怎么实现的？有什么坑？

**答**：每表带 `deleted` 字段，MyBatis-Plus 全局配置 `logic-delete-field: deleted`、`logic-delete-value: 1`、`logic-not-delete-value: 0`，之后 `selectById` 自动拼 `deleted=0`，`deleteById` 变 `UPDATE deleted=1`。

**最大的三个坑**：
1. **自定义 `@Select`/`@Update` SQL 不走逻辑删除自动注入**，必须手动加 `deleted=0`（如 `ReviewMapper.avgRatingByShop`）
2. **唯一索引与软删除冲突** —— 软删后唯一键仍占用，反复创建会撞唯一索引。生产通常用"唯一键 + deleted"组合，或软删时改字段值
3. **关联查询漏过滤** —— `JOIN` 其他表时，两张表的 `deleted` 都要过滤

> 考官想考察：是否真实现过软删除，且知道它与唯一索引、手写 SQL 的冲突。

---

### Q4：订单明细为什么要做快照？

**答**：商品会改价、下架甚至删除，收货地址会被修改。快照把下单那一刻的商品名/单价/收货信息固化进 `order_item` 和 `orders`，保证历史订单永远正确展示，符合交易一致性要求。CityGo 在 `OrderServiceImpl.create` 中把 `product` 和 `address` 的字段拷贝进订单。

**什么该快照、什么不该？** 收货信息/商品信息必须快照；店铺名称/用户昵称变化频率低，可关联查最新。

> 考官想考察：对电商交易数据一致性的理解，以及"历史数据不可变"的意识。

---

### Q5：shop.monthly_sales 这种冗余字段为什么划算？怎么保证一致性？

**答**：销量在列表页高频展示且频繁累加，冗余为单列后下单只需 `UPDATE monthly_sales = monthly_sales + ?`，避免每次 `COUNT` 订单明细，显著降低热点读写压力。

**一致性保证**：
1. **原子更新**：用数据库表达式 `SET monthly_sales = monthly_sales + ?`，不是先查再写
2. **事务包裹**：下单时累加，取消时回减，在同一个事务中
3. **CAS 校验**：库存扣减用 `WHERE stock >= ?`，返回 0 行即失败

**代价**：写操作变重，但换来了读操作的极大优化。

> 考官想考察：是否理解"空间换时间 / 避免聚合查询"的冗余设计思想，以及并发下的原子更新意识。

---

### Q6：为什么金额要用 DECIMAL 而不是 DOUBLE？

**答**：DOUBLE 是二进制浮点，存在精度误差（如 0.1 + 0.2 != 0.3），金额累计/对账会出现 0.30000000000000004 这类问题。DECIMAL 是精确定点数，`DECIMAL(10,2)` 保证两位小数精确。

**代码规范**：
- 所有金额字段用 `BigDecimal`
- 构造时用字符串 `new BigDecimal("0.1")`，不用 double
- 运算用 `multiply/add/subtract`
- 除法用 `divide(100, 2, RoundingMode.HALF_UP)` 显式指定精度和舍入

> 考官想考察：对浮点精度陷阱和金融级计算规范的敏感度。

---

### Q7：Flyway 已发布的迁移脚本能改吗？为什么？

**答**：不能。迁移脚本执行后记入 `flyway_schema_history` 并保存 checksum，改旧脚本会导致 checksum 不匹配，Flyway 校验失败拒绝启动。正确做法是新增 V6/V7 迁移。CityGo 的 V5 秒杀字段就是新增迁移（ALTER 加字段）而非改 V1。

**生产事故**：改了已执行的迁移 → `Migration checksum mismatch` → 服务启动失败。

**解决方案**：
- 开发环境：`flyway clean`（⚠️ 会清库，危险！）
- 生产环境：**绝对不能 clean**！只能手动修复 `flyway_schema_history` 表，或新增迁移修补

> 考官想考察：对数据库迁移工作流"不可变、可追溯"原则的理解。

---

### Q8：设计一个订单表，要考虑哪些？

**答**：从 8 个维度考虑：
1. **主键**：雪花 ID（分布式唯一）
2. **业务单号**：单独字段 `order_no`（字符串，对外展示）
3. **用户/店铺 ID**：逻辑外键 + 索引
4. **金额**：`DECIMAL(10,2)` —— total_amount, discount_amount, pay_amount
5. **状态**：`TINYINT`，区间化枚举
6. **快照**：收货人信息、商品信息固化
7. **时间**：create_time, update_time, paid_time, completed_time...
8. **公共字段**：deleted（软删除）
9. **索引**：`uk_order_no`, `idx_user_status`, `idx_create_time`

## f. 开发实战扩展

1. **唯一键与软删除冲突**：生产里 `uk_username` 这种唯一索引在软删除后会占用，重复创建同名用户撞唯一键。方案：唯一索引加 `deleted` 列（`uk(username, deleted)`），或软删时把 username 改成 `username_deleted_{id}`。

2. **大表分库分表**：雪花 ID 已经为分片做好准备；`orders` 这类大表生产会按 `user_id` 分片，`order_no` 做全局路由索引。

3. **迁移脚本纳入 CI**：生产把 Flyway 迁移接入 CI/CD，上线前先在 staging 跑一遍迁移并做 checksum 校验，防止线上结构漂移。

4. **在线 DDL**：MySQL 8 的 `ALTER` 默认 INPLACE，但对大表加字段仍要评估锁表风险，生产用 gh-ost / pt-osc 这类在线变更工具。

## g. 总结：面试 vs 工作的核心差异

| 维度 | 面试重点 | 工作重点 |
|------|---------|---------|
| 外键 | 能说清权衡（性能/扩展/一致性） | 老项目改造时别乱删 |
| 雪花 ID | 时钟回拨、前端精度丢失 | 监控 ID 生成性能 |
| 软删除 | 三个坑（SQL/唯一索引/关联查询） | 写代码时记得加 `deleted=0` |
| 快照 | 为什么做快照 | 控制快照字段数量，防表膨胀 |
| 冗余字段 | 怎么保证一致性 | 并发下用原子更新 |
| 状态机 | 区间化设计、CAS 更新 | 状态流转的日志审计 |
| 金额 | DECIMAL + BigDecimal | 绝对不用 double，除法指定舍入 |
| Flyway | 已发布不可改 | 团队协作规范、版本号管理 |
| 索引 | 最左前缀、覆盖索引 | EXPLAIN 分析实际执行计划 |
