# 13 评价与评分联动：一单一评、AVG 重算与缓存联动

> 本篇对应 CityGo 评价域：用户对已完成的订单评价、商家回复、店铺平均分联动更新。评价模块虽然"写"的频率不高，但它牵一发动全身——一条评价会影响店铺评分、店铺详情缓存、ES 搜索排序三处数据。学完本篇，你要能回答：怎么防止重复评价、为什么店铺平均分不能增量维护、以及一条评价写入后要联动更新哪些地方。

---

## a. 这个模块是干嘛的

CityGo 的用户在订单完成后可以对店铺打分（1-5 星）和留言，商家可以回复评价。评价的核心价值是**沉淀口碑**：店铺的 `score`（平均分）来自所有可见评价的 AVG，这个分又会进入店铺详情缓存和 ES 搜索排序，影响用户"按评分排序"看到的结果。所以这个模块的难点不在于 CRUD，而在于：

1. **评价资格的严格校验**：只能评价"自己的、已完成的"订单，且一单一评；
2. **评分联动的准确性**：平均分必须重算而非增量维护；
3. **联动失效的一致性**：评分变了，缓存和 ES 都要跟着更新，否则用户看到旧分。

一句话：这一篇讲的是**一条评价如何安全写入，并让"评分"这个下游数据准确且一致地传播**。

## c. 先懂概念

- **一单一评**：一个订单只能产生一条评价，用数据库唯一索引 `uk_order_id(order_id)` 硬性保证，业务层查重只是前置优化。
- **AVG 重算**：店铺平均分 = `AVG(所有可见评价的 rating)`。它不能像销量那样"加一减一"地增量维护，因为均值不是线性可加的。
- **冗余字段**：`review.shopId` 冗余自订单，评价列表按店铺查询时不用 join 订单表；代价是订单数据变了冗余不自动同步（本例订单归属不变，所以安全）。
- **逻辑删除与自定义 SQL**：MyBatis-Plus 的 `selectById` 等内置方法会自动拼 `deleted=0`，但自定义 `@Select` 不走这个增强，必须手动加 `deleted=0`。
- **联动失效**：上游数据（评分）变化后，依赖它的缓存、索引必须主动失效/刷新，否则读侧拿到旧值。

## d. 逐个详解

### d1. create 评价：六步写入 + 三层校验

`ReviewServiceImpl.create` 按注释 a→g 七步走读：

**a. 查订单 + 防探测**：`order == null || !order.getUserId().equals(currentUserId)` 都抛 `ORDER_NOT_FOUND`——**不区分"不存在"和"不是你的"**，统一返回 404，防止探测他人订单号（与 08 篇订单详情同样的语义）。

**b. 评价时机校验**：`order.getStatus() != OrderStatus.COMPLETED.getCode()`（50）即抛 `ORDER_STATUS_INVALID`。**为什么必须已完成**：未支付、已支付未完成、已取消的订单都不该能评价，否则用户没消费就能打分，评价体系失真。

**c. 防重复评价（业务查重）**：`reviewMapper.selectCount(orderId)` 大于 0 即抛 `REVIEW_ALREADY_EXISTS`。

**d. 插入评价 + DuplicateKeyException 兜底**：`review.setShopId(order.getShopId())` 冗余店铺 id，插入时 try-catch `DuplicateKeyException`——并发下两条同时插入同一订单，唯一索引 `uk_order_id` 保证只有一条成功，另一条转义为 `REVIEW_ALREADY_EXISTS`。这与 12 篇领券防重复是**完全相同的套路**：业务查重防 99%，唯一索引兜底防并发。

**e. 评分重算**：`reviewMapper.avgRatingByShop(order.getShopId())` 拿到平均分，非 null 则回写 `shop.score`。

**f. 缓存联动失效**：`shopBrowseService.evictDetailCache(order.getShopId())`——店铺详情缓存（`shopDetail::{id}`）里含 `score`，评分变了必须失效，下次访问重新查库拿到新分。

**f1. ES 近实时同步**：`searchSync.afterCommit(() -> shopSearchService.syncShop(...))`——ES 里店铺文档的评分用于"按评分排序"，评分变了要同步，否则排序用的是旧分。

**g. 返回视图**。

### d2. avgRatingByShop：为什么平均分必须"重算"

`ReviewMapper.avgRatingByShop` 的自定义 SQL：

```sql
SELECT AVG(rating) FROM review WHERE shop_id = #{shopId} AND status = 1 AND deleted = 0
```

类注释和 SQL 注释点破了几个关键：

1. **为什么重算而非增量维护**：平均分是 `AVG(rating)`，无法通过"加一条新评价"或"减一条旧评价"来增量更新——均值没有可加性。举例：原来 2 条评价（5、5），均值 5；再来一条 1 分，均值变成 (5+5+1)/3=3.67，你没法在旧均值 5 的基础上"加个增量"算出来。所以正确做法是**每次评价后重算 AVG**。对比销量、月销这类可累加字段，它们可以用 `sales = sales + 1` 增量维护（见 08 篇 `addMonthlySales`）。

2. **为什么 AVG 交给数据库聚合**：`AVG(rating)` 由 MySQL 聚合，避免把全部评价拉到内存再算——评价量大了内存扛不住。

3. **自定义 SQL 要手动加 `deleted=0`**：MyBatis-Plus 的逻辑删除是"增强"，内置方法自动拼 `deleted=0`；但 `@Select` 自定义 SQL 不走这个增强，注释里明确写了"手动加 `deleted=0`，与全局配置保持一致"。**坑在哪**：漏掉这个条件，已逻辑删除的评价会混进平均分统计，导致评分虚高或虚低。

### d3. reply 商家回复：归属校验 + 允许覆盖

`reply` 方法做两件事：

1. **归属校验**：评价所属店铺必须属于当前商家——`shop.getMerchantId().equals(merchant.getId())`，否则 `UNAUTHORIZED_OPERATION`。商家只能回复自己店铺收到的评价，不能跑去回复别家店的。
2. **更新回复（允许覆盖）**：直接 `updateById` 更新 `merchantReply` 和 `replyTime`，旧的回复被覆盖。这是业务上的选择——"回复"默认是覆盖式而非追加式。

### d4. 评价列表的 N+1 优化

`toPageVO` 分页转视图时，用 `distinct()` 收集当前页所有 `shopId` 和 `userId`，分别 `selectByIds` 批量拉店铺和用户，`toMap` 组装——**一次批量查询替代逐条查询**，避免 N+1。评价列表要展示店铺名、用户昵称、头像，如果不批量，每条评价要分别查一次店铺和用户，20 条评价就是 40 次查询。

`listShop` 只查 `status=1`（展示中）的评价；`pageMy` 查当前用户的全部评价（含隐藏的，因为"我的评价"要给用户看自己的历史）。

### d5. 评分联动的完整数据流

一条评价写入后，评分数据要传播到三个地方，`create` 方法里依次处理：

```
评价写入 (review)
   ↓ e. AVG 重算
shop.score 更新 (MySQL 主库)
   ↓ f. 缓存失效
shopDetail::{id} 删除（下次读重新查库回填）
   ↓ f1. afterCommit 同步
ES 店铺文档 score 更新（评分排序用最新值）
```

**为什么缓存是"失效"而 ES 是"同步"**：店铺详情缓存（Spring Cache）用 `@Cacheable` 被动回填，所以只删 key、下次读自动重建；ES 是独立的搜索引擎，需要主动把最新文档写进去，否则索引里是旧分。两套体系用两种联动方式，与 09 篇"两套缓存体系失效联动"一脉相承。

## e. 面试真题

**Q1：怎么防止一个订单重复评价？**
结合 CityGo：和领券防重复同套路——业务层先 `selectCount(orderId)` 查重，存在即拒；数据库层用唯一索引 `uk_order_id(order_id)` 兜底，并发下两条同时插入时 `DuplicateKeyException` 转义为 `REVIEW_ALREADY_EXISTS`。业务查重防 99% 场景，唯一索引兜住并发"同时查没查到、同时插"。
考官想考察什么：能否把"唯一索引兜底 + 业务查重"这个防重复套路迁移到评价场景，讲清两者的分工。

**Q2：评价的时机怎么校验？为什么必须订单已完成？**
结合 CityGo：`create` 里校验 `order.getStatus() == OrderStatus.COMPLETED.getCode()`（50），非已完成抛 `ORDER_STATUS_INVALID`。如果允许未支付、未完成的订单评价，用户没实际消费就能打分，评价体系失真——"评价"必须建立在真实成交之上。
考官想考察什么：是否理解评价与订单状态机的关系，以及校验时机对业务合法性的意义。

**Q3：店铺平均分为什么"重算"而不是"增量维护"？**
结合 CityGo：平均分 `AVG(rating)` 没有可加性——2 条 5 分均分 5，再来 1 分变 3.67，无法在旧均值上"加增量"得出。所以 `avgRatingByShop` 每次评价后重算 AVG 回写 `shop.score`。对比销量、月销这类可累加字段可以用 `sales = sales + 1` 增量维护。
考官想考察什么：能否区分"可增量维护的累加量"与"必须重算的聚合量"，这是数据一致性设计的基本功。

**Q4：一条评价写入后要联动更新哪些地方？**
结合 CityGo：三处——①`shop.score` 重算回写（主库）；②失效店铺详情缓存 `shopDetail::{id}`（缓存里含 score）；③`afterCommit` 同步 ES 店铺文档（评分排序用最新值）。缓存用"失效被动重建"，ES 用"主动同步"，两套体系两种联动方式。
考官想考察什么：能否完整列出评分传播的下游，并区分"缓存失效"与"索引同步"两种策略。

**Q5：自定义 @Select 的 avgRatingByShop 为什么要手动加 deleted=0？**
结合 CityGo：MyBatis-Plus 的逻辑删除是内置方法的增强，自动拼 `deleted=0`；但 `@Select` 自定义 SQL 不走增强，必须手动加 `deleted=0`，否则已逻辑删除的评价会混进平均分统计。注释里专门强调了这点。
考官想考察什么：是否理解逻辑删除的实现边界——"增强只对内置方法生效，自定义 SQL 要自己兜底"。

**Q6：商家回复评价怎么校验权限？**
结合 CityGo：`reply` 里先查评价，再校验"评价所属店铺的 merchantId 是否等于当前商家 id"，不是自己的店铺抛 `UNAUTHORIZED_OPERATION`。商家只能回复自己店铺收到的评价，不能越权回复别家店的。
考官想考察什么：能否识别出"资源归属校验"这一贯穿全项目的安全模式（与商品、店铺、订单的归属校验一致）。

**Q7：评价列表展示店铺名和用户昵称，怎么避免 N+1？**
结合 CityGo：`toPageVO` 用 `distinct()` 收集当前页所有 shopId 和 userId，分别 `selectByIds` 批量拉店铺和用户，`toMap` 组装，一次批量查询替代逐条查询。20 条评价如果不批量，会额外产生 40 次单点查询。
考官想考察什么：能否识别 N+1 问题并给出"批量 in 查询 + Map 组装"的标准解法。

## f. 开发实战扩展

- **评分用异步重算**：CityGo 在评价事务里同步重算 AVG，评价量大时写路径会变慢。生产会把评分重算拆到 **MQ 异步**（评价成功发消息，消费者重算评分），或用 **Redis 计数器 + 定时批量落库** 缓解实时压力，但要以"允许评分短暂延迟"为前提。
- **评分可信度治理**：简单 AVG 会被刷分（差评师/好评返现）扭曲，生产会引入**加权评分**（如按时间衰减、按用户可信度加权）或**疑似刷单过滤**，而不是裸 AVG。
- **评价内容审核**：生产对评价文本/图片会接**敏感词过滤 + 人工审核**，审核通过才 `status=1` 展示，而不是插入即展示。
- **商家回复通知**：回复后应通知用户（CityGo 的支付通知已有 Redis List 通道可复用），生产会接站内信/推送。
