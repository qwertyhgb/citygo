# 01 · 项目骨架与工程实践

> 本篇覆盖：Spring Boot 4.1 工程结构、starter 新命名、多环境配置、Result 统一返回、ErrorCode / BizException / GlobalExceptionHandler、springdoc、logback、Flyway 引入与 BOM 版本管理、jjwt 0.13 新 API、Maven 本地仓库与阿里云镜像实践。

## a. 这个模块是干嘛的

CityGo 是一个模拟美团核心业务的本地生活服务平台（学习项目），整个后端从 0 搭起的第一步不是写业务，而是把"工程地基"打牢：统一返回结构、统一异常处理、统一日志、数据库迁移版本管理、接口文档自动生成、JWT 依赖引入。这一层决定了后续 14 张表、十几个业务包是"在泥地上盖楼"还是"在混凝土地基上盖楼"。面试时问的"你们项目怎么统一错误码""为什么 HTTP 永远 200"，答案全部藏在这一篇里。

## c. 先懂概念

1. **Spring Boot Starter 命名大改**：Spring Boot 4 起，`spring-boot-starter-web` 改名为 `spring-boot-starter-webmvc`，`spring-boot-starter-aop` 改名为 `spring-boot-starter-aspectj`。老项目迁移 SB4 时如果还写旧名，依赖会直接找不到。
2. **BOM 版本管理**：parent 是 `spring-boot-starter-parent`，它内部用 dependencyManagement 锁定了一大批依赖版本（Flyway、Security、Redis、AMQP、ES 等），所以 pom 里这些依赖**都不写 `<version>`**；只有 BOM 没管的（MyBatis-Plus、springdoc、jjwt）才手写版本号。
3. **HTTP 200 + 业务码**：整个系统的 HTTP 状态码恒为 200，真正的成败放在返回体 `code` 字段。网关、日志、监控只关心传输层是否通，业务语义由前端看 `code` 分流。
4. **业务异常与系统异常分离**：业务异常（BizException）是"预期内的、有业务解释的"，用 WARN 记日志、文案可安全暴露；系统异常是程序缺陷，用 ERROR 记堆栈、返回统一兜底文案。
5. **Flyway 版本迁移**：数据库结构变更全部写成带版本号的 SQL 脚本，启动时按序执行并记录到 `flyway_schema_history`，保证 dev/test/prod 三套环境库结构一致。

## d. 逐个详解

### 1. pom.xml：为什么依赖要这么引

工程 parent 锁定 `spring-boot-starter-parent:4.1.1`，Java 版本 21。几个值得面试讲的点：

- **webmvc 新命名**：`spring-boot-starter-webmvc` 是 SB4 对旧 `spring-boot-starter-web` 的重命名；测试侧对应 `spring-boot-starter-webmvc-test`。
- **模块化 -test starter**：SB4 把每个 starter 的测试能力拆成独立 starter，如 `spring-boot-starter-actuator-test`、`spring-boot-starter-validation-test`。测试依赖不再隐式跟主 starter 走。
- **aspectj starter**：`spring-boot-starter-aspectj` 是旧 `spring-boot-starter-aop` 的新名。关键点：**SB4 的 webmvc starter 不再传递包含 AOP**，所以用了 `@Aspect`/`@Around` 就必须显式引入它，否则切面不生效。
- **MyBatis-Plus 两个坐标**：`mybatis-plus-spring-boot4-starter:3.5.17` 是主启动器；`mybatis-plus-jsqlparser:3.5.17` 是 3.5.9+ 把 `PaginationInnerInterceptor` 从 extension 拆出来的新模块，**不引它分页插件直接 ClassNotFound**。
- **Flyway 拆模块**：`spring-boot-starter-flyway`（自动装配）+ `flyway-mysql`（Flyway 10+ 把数据库支持拆成独立模块，不引会报 `Unsupported Database: MySQL`）。
- **jjwt 0.13 三件套**：`jjwt-api`（编译期）、`jjwt-impl` + `jjwt-jackson`（runtime）。这是官方推荐的拆分方式。
- **springdoc 3.1.0**：官方基于 Spring Boot 4.1 构建，与当前版本匹配。

### 2. Result：为什么 HTTP 200 + 业务码

`Result<T>` 三个字段 `code`、`message`、`data`。构造器私有，只能走静态工厂 `success()` / `success(data)` / `error(ErrorCode)` / `error(code, message)`。

设计取舍写在类注释里：**HTTP 状态码始终保持 200，业务成败放在 `Result.code`**。这样：

- 网关、日志、监控不需要解析业务状态，传输层与业务层解耦；
- 前端在 HTTP 200 基础上按 code 分流，统一弹窗/跳转；
- 配合全局异常处理器，异常堆栈不会被暴露给调用方。

坑：很多人会问"那 RESTful 语义怎么办"。答案是：本项目是**学习项目**，采用企业里也很常见的"业务码方案"，HTTP 状态码只表达传输结果；真正 RESTful 的话会用 201/404/409 等状态码，两种风格都对，关键是**全项目统一**。

### 3. ErrorCode / BizException / GlobalExceptionHandler 三件套

`ErrorCode` 枚举按 Phase 分块追加：通用码（400/401/403/404/409/500）→ 认证域（`USERNAME_ALREADY_EXISTS`、`BAD_CREDENTIALS`、`TOKEN_INVALID`）→ 商家/商品域 → 订单域 → Redis 专题（`REPEAT_SUBMIT`、`TOO_MANY_REQUESTS`）→ 优惠券域 → 评价域 → 秒杀域（`SELL_NOT_AVAILABLE` 等）。注释特别强调：**不要把所有码堆在公共枚举里**，业务阶段在各自包扩展，避免枚举膨胀。

`BizException` 继承 `RuntimeException`，持有 `ErrorCode`。它的意义是**与系统异常分离**：业务异常是预期内的（参数错、资源不存在），系统异常是缺陷（空指针、连接失败）。

`GlobalExceptionHandler` 用 `@RestControllerAdvice`，处理顺序值得背：

| 异常类型 | 日志级别 | 返回 |
| --- | --- | --- |
| `BizException` | WARN | `Result.error(e.getErrorCode())` |
| `AuthorizationDeniedException`（@PreAuthorize 拒绝） | WARN | 403 |
| `MethodArgumentNotValidException`（@Valid 字段校验） | WARN | 取第一条 `field: 提示` |
| `ConstraintViolationException` | WARN | 400 |
| `HttpMessageNotReadableException`（JSON 格式错） | WARN | "请求体格式错误" |
| `MethodArgumentTypeMismatchException`（参数类型错） | WARN | "参数类型错误" |
| `NoResourceFoundException` | WARN | 404 |
| `Exception`（兜底） | ERROR + 完整堆栈 | 统一 500 |

坑：兜底异常**不返回 `e.getMessage()`**。类注释写得很清楚：异常详情可能泄露 SQL、内部字段，返回给调用方有安全风险。面试常问"全局异常处理为什么不直接透传 message"，答案就是这条。

### 4. springdoc 与 Swagger UI

`OpenApiConfig` 里 new 了一个 `OpenAPI` 实例并配置 `Info`（标题 CityGo API、版本 0.1.0）。springdoc 启动时扫描所有 `@RestController` + `@Tag`/`@Operation` 注解生成 OpenAPI 3 文档。

`application.yml` 里配了路径：JSON 规范在 `/v3/api-docs`，UI 在 `/swagger-ui.html`。这两个路径在 `SecurityConfig` 里被 permitAll 放行，未登录也能看接口文档。

### 5. logback 日志分级

`logback-spring.xml` 定义了 CONSOLE + 按天滚动的 FILE（`logs/citygo-server.log`，最多保留 30 天）。关键点：

- 文件名必须是 `logback-spring.xml` 才能识别 `<springProfile>` 标签；
- dev 环境业务包 `com.citygo` 输出 DEBUG，非 dev 输出 INFO；
- 日志分级语义：ERROR 系统故障必须打印堆栈、WARN 预期内异常、INFO 业务流转。

### 6. Flyway 引入与 BOM 版本管理

Flyway 版本号由 Spring Boot BOM 管理（pom 里不写 version），`application.yml` 配置 `spring.flyway.enabled=true`、`locations=classpath:db/migration`、`encoding=UTF-8`。Flyway 每次启动按版本号顺序执行未执行的脚本，写入 `flyway_schema_history`。

坑（pom 注释明确写了）：**Flyway 10+ 把数据库支持拆成独立模块**，MySQL 必须额外引 `flyway-mysql`，否则启动报 `Unsupported Database: MySQL`。这是 SB4/Flyway 10 时代的一个高频踩坑点。

### 7. jjwt 0.13 新 API

`JwtUtil` 是 jjwt 0.13 新 API 的示范（在 03 篇会展开），这里只记骨架：

- 生成：`Jwts.builder().subject(userId).claim("username", ...).issuedAt(now).expiration(expiry).signWith(key).compact()`
- 解析：`Jwts.parser().verifyWith(key).build().parseSignedClaims(token).getPayload().getSubject()`
- 严禁用旧版已废弃的 `setSubject` / `parseClaimsJws`（类注释点名批评）。

另外注意 Jackson 已切到 `tools.jackson`（Jackson 3）：`tools.jackson.databind.json.JsonMapper`，这是 SB4 的内置 Jackson 版本，与 SB3 的 `com.fasterxml.jackson` 不同。

### 8. Maven 本地仓库 / 阿里云镜像实践

pom 本身不含仓库配置（仓库配置在用户级 `~/.m2/settings.xml`）。实践要点：国内环境在 `settings.xml` 配阿里云镜像 `<mirror><id>aliyunmaven</id><mirrorOf>central</mirrorOf><url>https://maven.aliyun.com/repository/public</url></mirror>`；本地仓库默认在 `~/.m2/repository`，可通过 `<localRepository>` 改路径。Spring Boot 4.1.1 是很新的版本，如果拉不到，检查镜像是否同步了 spring milestone/release 仓库。

## e. 面试真题

**Q1：你们项目为什么 HTTP 状态码永远返回 200？这不是违反 RESTful 吗？**

答：CityGo 用「HTTP 200 + 业务码」方案：`Result.code` 承载 200/400/401/403/409/500 等业务语义，HTTP 层恒为 200。好处是网关、监控、日志不需要解析业务状态，前端在 HTTP 200 基础上统一按 code 分流。代价是损失 RESTful 状态码语义。两种风格都对，关键是全项目统一；如果是严格 REST 接口我会改用 201/404/409 等状态码。

> 考官想考察：是否理解"传输层状态"与"业务层状态"的区分，而不是死记 RESTful 教条。

**Q2：全局异常处理器为什么兜底异常不直接返回 e.getMessage()？**

答：因为异常详情可能包含 SQL 语句、内部字段名、调用栈等敏感信息，直接透传给调用方有安全隐患；调用方需要的是稳定可读的统一文案。CityGo 的做法是兜底异常记 ERROR 完整堆栈（供开发排查），只返回统一的"服务器内部错误"；业务异常则记 WARN 并返回对应业务码文案。

> 考官想考察：是否理解"信息暴露面"与"可观测性"的平衡——错误要记全、给用户要少。

**Q3：Spring Boot 4 相比 3.x 有哪些 starter 命名变化？迁移要注意什么？**

答：`web` 改为 `webmvc`（对应 `-test` 后缀测试 starter）、`aop` 改为 `aspectj`、测试 starter 模块化拆分（`-test` 后缀独立引入）。最大的坑是：SB4 的 webmvc starter 不再传递 AOP，用了切面必须显式引 `spring-boot-starter-aspectj`；Flyway 10+ 需要额外引 `flyway-mysql`。

> 考官想考察：是否真的动过 SB4 工程，而不是只会背 SB2/3 的套路。

**Q4：你们的错误码是怎么组织的？为什么不全部放一个枚举里？**

答：`ErrorCode` 枚举按业务阶段分块追加，通用码在前、各业务域码在后。注释里明确写了：不把所有码堆在公共枚举里，避免膨胀，后续业务阶段在各自包里扩展。这样每个 Phase 的错误码职责清晰、不会互相干扰。

> 考官想考察：是否理解"枚举膨胀"的工程问题与按域分层的思想。

**Q5：为什么业务异常要继承 RuntimeException 而不是 CheckedException？**

答：业务异常是运行期可预期的，用运行时异常可以让业务代码不需要到处 `throws`/`try-catch`，配合 `@RestControllerAdvice` 统一拦截即可；CheckedException 会强迫每一层声明或捕获，反而污染代码。CityGo 的 `BizException extends RuntimeException`，由 `GlobalExceptionHandler` 统一转成 Result。

> 考官想考察：对异常体系设计的理解，以及为什么现代框架普遍用运行时异常。

**Q6：springdoc 和 springfox 有什么区别？你们为什么用 springdoc？**

答：springfox 对 Spring Boot 3+ 支持基本停摆；springdoc 是 OpenAPI 3 规范的实现，官方基于 Spring Boot 4.1 构建，开箱即用 Swagger UI，注解用标准 `@Tag`/`@Operation`。CityGo 用 `springdoc-openapi-starter-webmvc-ui:3.1.0`，JSON 规范在 `/v3/api-docs`，UI 在 `/swagger-ui.html`。

> 考官想考察：选型理由，以及对 OpenAPI 3 规范的了解。

## f. 开发实战扩展

1. **生产环境错误码要带 traceId**：这里 Result 只有 code/message/data，生产建议加一个 `traceId`（从 MDC 取），前端报错时带上，方便日志链路定位。
2. **错误码平台化管理**：大厂会把错误码做成配置中心下发（码表 + 文案 + 建议），而不是硬编码枚举，方便多语言和运营调整文案。
3. **日志采集升级**：这里 logback 落本地文件，生产会接入 ELK/Loki + OpenTelemetry 做集中采集与链路追踪，日志要带上 requestId。
4. **Maven 私服**：企业内不用阿里云镜像，而是 Nexus/Artifactory 私服统一代理与缓存，版本收敛靠 BOM + 依赖锁（如 lock 文件或版本号平台）。
