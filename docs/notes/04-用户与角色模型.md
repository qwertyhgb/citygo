# 04 · 用户与角色模型

> 本篇覆盖：user / role / user_role 多对多模型、注册事务、登录防撞库统一错误码、@MapperScan。

## a. 这个模块是干嘛的

CityGo 有三类身份：普通用户（USER）、商家（MERCHANT）、管理员（ADMIN），但他们都落在同一张 `user` 表里，身份差异靠"角色"表达。用户与角色是多对多关系（一个用户可以有多个角色，比如既是用户又是商家），通过中间表 `user_role` 关联。这一篇讲清楚"账号与身份解耦"这个设计，以及注册时怎么在事务里同时建账号、绑角色。

## b. 文件一览

| 文件路径 | 职责 |

## c. 先懂概念

1. **账号与身份解耦**：`user` 表只存账号信息（用户名/密码/手机号），"是不是商家"由是否绑了 `MERCHANT` 角色决定，不在 user 表加 `is_merchant` 字段。这样后续加新身份（如骑手）不用改 user 表。
2. **多对多关联**：用户-角色是标准多对多，中间表 `user_role` 存 `(user_id, role_id)`，`uk_user_role` 唯一索引防止同一用户重复绑同一角色。
3. **RBAC**：Role-Based Access Control，基于角色的访问控制。CityGo 是简化版 RBAC：用户 → 角色 → 权限（`ROLE_xxx`），没有单独的权限表，角色直接对应 Spring Security 的 authority。
4. **VO 与 Entity 分离**：`User` 实体含 password，`UserVO` 不含 password，对外只返回 VO，避免密码泄露。
5. **@MapperScan**：在启动类上统一扫描 Mapper 接口，替代逐个 `@Mapper` 注解。

## d. 逐个详解

### 1. 三张表的关系

- `user`：`uk_username` 唯一索引，`password` 存 BCrypt 密文，`status` 1 正常 0 禁用，公共字段 `deleted` 软删除。
- `role`：`uk_code` 唯一索引，code 是稳定标识（USER / MERCHANT / ADMIN），name 是展示名。
- `user_role`：`uk_user_role(user_id, role_id)` 防重复绑定，`idx_role_id` 支持"某角色下有哪些用户"的反向查询。

实体层面：`User` 用 `@TableId(type = IdType.ASSIGN_ID)` 生成雪花主键，注释明确"逻辑删除字段 deleted 由 MyBatis-Plus 全局配置（logic-delete-field）自动生效，本实体仅需保留该属性，无需额外 @TableLogic 注解"。

### 2. @MapperScan 统一扫描

`CityGoApplication` 上 `@MapperScan("com.citygo.**.mapper")`，通配符 `**` 匹配任意层级包，所以 auth/user/merchant/... 各业务包下的 Mapper 都会被自动扫描注册，不用每个接口写 `@Mapper`（虽然各 Mapper 上还是写了 `@Mapper`，但扫描是兜底保证）。

### 3. 注册事务：建账号 + 绑角色

`AuthServiceImpl.register` 是 `@Transactional(rollbackFor = Exception.class)`：

1. 查 `userService.getByUsername`，存在则抛 `USERNAME_ALREADY_EXISTS`；
2. 新建 `User`：username、BCrypt 加密密码、昵称默认取用户名、status=1，insert；
3. 查 `role` 表 `code = "USER"`，查不到抛 `INTERNAL_ERROR`；
4. 新建 `UserRole(userId, roleId)` 并 insert。

**为什么必须事务**：如果建了 user 但绑角色失败，会留下"没有角色的幽灵用户"（登录后无任何权限，且安全过滤器里 authorities 为空）。事务保证两步要么都成功要么都回滚。

### 4. UserServiceImpl：角色组装

`UserServiceImpl` 负责把"用户 + 角色"组装成 `UserVO`：

- `getByUsername` / `getById`：直接 `selectOne`/`selectById`；
- `getRoleCodes(userId)`：先查 `user_role` 拿 roleIds，再 `roleMapper.selectByIds(roleIds)` 拿角色，映射成 code 列表；
- `toUserVO(user)`：把 User 实体拷贝成 UserVO，并填充 roles。

注意注释点：虽然 `RoleMapper`/`UserRoleMapper` 归属于 auth 域，但"用户携带哪些角色"是用户信息的一部分，在 UserServiceImpl 统一组装，供注册/登录/我的信息复用。这是**跨包复用的合理归属**。

### 5. 登录防撞库统一错误码

（03 篇已详细讲，这里补充用户域视角）`login` 里三处失败统一抛 `ErrorCode.BAD_CREDENTIALS`：

- `user == null`（用户不存在）
- `user.getStatus() == 0`（账号禁用）
- `passwordEncoder.matches` 失败（密码错）

三者对外完全一样，防止攻击者用"用户名不存在/密码错误"的返回差异枚举注册用户。`USER_DISABLED(403, "账号已被禁用")` 这个错误码虽然定义了，但登录场景故意不用，避免泄露"这个账号存在且被禁用"。

### 6. UserVO 脱敏

`UserVO` 字段：id、username、nickname、avatar、phone、status、roles。**没有 password**。`toUserVO` 从 User 拷贝时天然跳过 password，从源头防止密码泄露到 API 响应。

`/api/users/me` 接口从 `SecurityContextHolder.getContext().getAuthentication().getPrincipal()` 强转 userId（过滤器认证时 principal 就是 userId），查库后返回 `toUserVO`。

## e. 面试真题

**Q1：为什么商家账号不单独建一张表，而是和普通用户共用 user 表？**

答：商家与用户本质是同一类"账号"，只是角色不同。共用 user 表 + MERCHANT 角色，账号体系统一（登录/密码/禁用逻辑复用），商家额外资料放 `merchant` 表通过 `user_id` 逻辑关联。好处是身份可叠加（一个用户既可以是 USER 也可以是 MERCHANT）、加新身份不改 user 表；代价是角色关系要多查一张中间表。

> 考官想考察：对"账号统一、身份分离"设计的理解，而非见一个角色建一张表。

**Q2：用户-角色多对多怎么建模？为什么中间表要加唯一索引？**

答：`user_role(user_id, role_id)` 中间表，`uk_user_role(user_id, role_id)` 唯一索引防同一用户重复绑同一角色（数据幂等兜底），`idx_role_id` 支持反向查"某角色下有哪些用户"。业务层注册时先查 code 再插关联，唯一索引是最后一道防线。

> 考官想考察：多对多建模的基本功，以及唯一索引做幂等兜底的意识。

**Q3：注册为什么要放在事务里？**

答：注册 = 建 user + 查角色 + 绑 user_role，三步必须原子。如果建了 user 但绑角色失败，会留下没有角色的幽灵用户（登录后 authorities 为空、无任何权限）。`@Transactional(rollbackFor = Exception.class)` 保证要么都成功要么都回滚。

> 考官想考察：对"多步写操作需事务保证原子性"的敏感度。

**Q4：UserVO 为什么要和 User 实体分开？**

答：User 实体含 password 等敏感字段，直接返回实体等于把密码暴露给前端。UserVO 只保留 id/username/nickname/avatar/phone/status/roles，toUserVO 拷贝时天然跳过 password，从源头防泄露；同时 VO 补了 roles（角色编码列表），是"组装后"的展示形态。

> 考官想考察：Entity/VO 分层与敏感字段脱敏意识。

**Q5：@MapperScan 的作用是什么？**

答：`@MapperScan("com.citygo.**.mapper")` 在启动类上统一扫描所有业务包的 Mapper 接口，替代在每个接口上逐个写 @Mapper。通配 `**` 匹配任意层级包，新增 Mapper 只要放进对应包就自动注册。

> 考官想考察：对 MyBatis Mapper 注册机制的了解。

**Q6：账号被禁用了，登录接口会返回"账号已被禁用"吗？**

答：不会。虽然定义了 `USER_DISABLED(403, "账号已被禁用")`，但登录场景故意不用它——用户不存在、密码错、账号禁用统一返回 `BAD_CREDENTIALS("用户名或密码错误")`，防止攻击者探测"这个账号存在且被禁用"。禁用状态只在已登录后访问受限接口时才体现。

> 考官想考察：对防撞库/防探测与错误码取舍的深度理解。

## f. 开发实战扩展

1. **RBAC 完整化**：这里是"用户-角色"两级，真实系统是"用户-角色-权限"三级，权限是细粒度资源+操作（如 `order:create`），角色是权限的集合，可用 Spring Security 的 hasAuthority + 权限表实现。
2. **角色数据字典化**：role 表 + code 常量化，生产会抽成枚举或配置，避免魔法字符串 `"USER"` 散落代码。
3. **多租户**：SaaS 场景 user 会加 tenant_id 维度，所有查询按租户隔离。
4. **账号安全加固**：注册加图形验证码/短信验证码、密码复杂度校验、登录失败次数限制（防爆破），这些在 CityGo 里都简化掉了。
