# 06 · 商品与分类

> 本篇覆盖：product / category 模型、商品 CRUD / 上下架 / 调库存、分页插件（PaginationInnerInterceptor + DbType 新写法）、PageVO 设计（不暴露 MP 对象）、公开脱敏（stock 置 null）、N+1 批量查询优化、热门商品接口（getHotProducts 概要，缓存三防详见 09 篇）、秒杀商品列表接口（getSeckillProducts）。

## a. 这个模块是干嘛的

商品是交易的核心资源：商家在店铺里上架商品（挂靠分类），用户浏览、加购、下单。这一篇除了商品 CRUD，更重要的是五个工程实践：**分页怎么做**（MP 分页插件 + PageVO 封装）、**公开接口怎么脱敏**（库存不暴露给用户）、**N+1 查询怎么优化**（批量预取分类名/店铺名）、**热门商品怎么做**（手写缓存三防，详见 09 篇）、**秒杀商品列表**（不缓存、直接查库）。这几个点是面试里"你写过列表接口吗"的高频追问。

## c. 先懂概念

1. **分页插件**：MyBatis-Plus 的 `PaginationInnerInterceptor` 拦截 SQL，自动追加 `LIMIT` 并做 count 查询，配合 `Page` 对象使用。
2. **DbType 新写法**：MP 3.5.9+ 用枚举 `DbType.MYSQL`，不用旧版字符串常量；且分页插件拆到了 `mybatis-plus-jsqlparser` 模块。
3. **PageVO 封装**：把 MP 的 `Page` 转成不含 MP 依赖的轻量结构返回前端，避免暴露内部实现。
4. **脱敏**：公开接口不返回库存（stock 置 null），库存是商家经营数据。
5. **N+1 问题**：循环查库（查一条商品查一次分类名），改为批量 `selectByIds` 一次取回映射。

## d. 逐个详解

### 1. product / category 模型

- `Product`：id、shopId、categoryId、productName、description、coverImage、images、price、originalPrice、seckillPrice、seckillStock、seckillStart、seckillEnd（V5 加的秒杀字段）、stock、sales、status（1 上架 0 下架）。

- `Category`：id、parentId（0 表示一级）、categoryName、icon、sort、status。V3 预置 6 个一级分类。

索引设计（02 篇已讲）：`idx_shop_status(shop_id, status)` 支撑"店铺内查上架商品"，`idx_category_id` 支撑分类列表，`idx_price` 支撑价格筛选。

### 2. 分页插件配置

`MybatisPlusConfig`：

```java
@Bean
public MybatisPlusInterceptor mybatisPlusInterceptor() {
    MybatisPlusInterceptor interceptor = new MybatisPlusInterceptor();
    interceptor.addInnerInterceptor(new PaginationInnerInterceptor(DbType.MYSQL));
    return interceptor;
}
```

坑（注释强调）：DbType 用 3.5.9+ 的**枚举写法** `DbType.MYSQL`，勿用旧版字符串常量；且分页插件依赖 `mybatis-plus-jsqlparser`（pom 里有注释：MP 3.5.9+ 把 PaginationInnerInterceptor 从 extension 拆到此模块，不引直接 ClassNotFound）。

### 3. PageVO：不暴露 MP 对象

`PageVO<T>` 只有 records/total/pageNum/pageSize 四个稳定字段，构造器接收 MP 的 `Page<T>` 转出来。注释写明：**避免把 MP 内部实现暴露给调用方，也更易序列化**。所有分页接口（商品、店铺、订单、券、评价、搜索）都返回 PageVO。

坑：`PageVO` 的 `pageNum`/`pageSize` 是 `long`，构造时从 `page.getCurrent()`/`page.getSize()` 取。

### 4. 商品 CRUD 与归属校验

`ProductServiceImpl` 复用 05 篇的两级校验模式：

- `requireMerchant(currentUserId)`：确认是商家；

- `requireOwnedShop(shopId, merchantId)`：店铺必须属于该商家；

- `requireOwnedProduct(productId, merchantId)`：先查商品（不存在抛 `PRODUCT_NOT_FOUND`），再校验其 shopId 归属（越权抛 403）。

`create`：校验分类存在（`categoryMapper.selectById`）→ 校验店铺归属 → 组装商品（默认上架、销量 0）→ insert → `syncProductAfterCommit` 同步 ES。
`update`：`@CacheEvict(cacheNames = "productDetail", key = "#id")` 失效详情缓存 → 部分更新 → 失效热门缓存 → 同步 ES。
`updateStatus`：上下架，`@CacheEvict("productDetail")` + 失效热门缓存 + 同步 ES（下架商品 ES 文档保留但 status=0，便于重新上架）。
`updateStock`：改库存，同样三连（失效详情 + 失效热门 + 同步 ES）。

> **缓存失效"三连"**：`update`/`updateStatus`/`updateStock` 三个写操作都遵循同一模式——先 `@CacheEvict` 失效 Spring Cache 管理的商品详情缓存，再 `evictHotProductsCache()` 手动删除手写热门缓存（因为两套缓存 key 空间不同，注解失效不了手写缓存，详见 09 篇 d5），最后同步 ES。这是"先改库，再失效缓存"的旁路失效模式。

### 5. 公开接口脱敏

`pagePublic` 和 `getPublicDetail` 里，组装完 ProductVO 后 `vo.setStock(null)`。注释：**库存属商家内部经营数据，不向用户端暴露**。所以同一个商品，商家侧 `/api/products/my` 能看到 stock，用户侧 `/api/products` 看不到。

`pagePublic` 还做了：只查上架商品（`eq(Product::getStatus, 1)`）、指定店铺时校验店铺存在且营业、排序白名单映射（sales/price\_asc/price\_desc/default）。

### 6. 排序白名单防注入

`pagePublic` 的排序字段用 switch 白名单映射：

```java
switch (sortKey) {
    case "sales" -> qw.orderByDesc(Product::getSales).orderByDesc(Product::getId);
    case "price_asc" -> qw.orderByAsc(Product::getPrice).orderByDesc(Product::getId);
    case "price_desc" -> qw.orderByDesc(Product::getPrice).orderByDesc(Product::getId);
    default -> qw.orderByDesc(Product::getId);
}
```

注释：**排序字段必须白名单映射，防止 SQL 注入**——绝不把用户输入的 sort 直接拼进 SQL，而是映射到 LambdaQueryWrapper 的方法引用。`ShopBrowseServiceImpl` 的排序是同样的套路。

### 7. N+1 批量查询优化

`pageMy` 和 `pagePublic` 都要给商品补分类名，如果逐条查（每条商品 `selectById(categoryId)`）就是 N+1。`loadCategoryNames` 的做法：

```java
List<Long> categoryIds = products.stream().map(Product::getCategoryId).distinct().toList();
return categoryMapper.selectByIds(categoryIds).stream()
        .collect(Collectors.toMap(Category::getId, Category::getCategoryName));
```

先收集去重的 categoryId，一次 `selectByIds` 取回，转成 Map，组装 VO 时 `getOrDefault` 查表。N 次查询降为 1 次。同样的批量预取模式在 `ReviewServiceImpl.toPageVO`（店铺名 + 昵称）、`ProductSearchServiceImpl.syncProducts`（店铺名 + 分类名）、`CouponServiceImpl.pageMy`（券模板）里反复出现。

### 8. pageMy 的多店铺限定

商家查"我的商品"时，如果不指定 shopId，`pageMy` 先查该商家名下所有店铺 id，再 `qw.in(Product::getShopId, myShopIds)`，避免数据越权（看到别人的商品）。店铺为空直接返回空 PageVO。

### 9. 热门商品：getHotProducts（概要，缓存三防详见 09 篇）

`GET /api/products/hot?limit=10` 是用户端高频接口，返回销量 top N 的上架商品，带 `@RateLimit(limit = 5, windowSeconds = 1)` 限流。方法整体流程：

```
请求 → 读缓存 → 命中 → sliceHot 切片返回
               ↓ 未命中
             抢互斥锁 → 抢到 → double-check → 查库 → 写缓存 → 返回
             抢不到 → 睡 100ms × 3 重试 → 仍无 → 降级查库
```

几个关键设计决策（09 篇有完整代码走读，这里只列要点）：

| 设计点                   | 说明                                                                                                          |
| --------------------- | ----------------------------------------------------------------------------------------------------------- |
| **入参夹逼**              | `safeLimit = clamp(limit, 1, 50)`，防恶意大值拉全表                                                                  |
| **缓存权威长度**            | 缓存固定存 top 50（`MAX_HOT_LIMIT`），不按请求 limit 灌缓存；每个请求用 `sliceHot()` 切片返回自己需要的条数——避免小 limit 请求灌的缓存坑了后续大 limit 请求 |
| **防击穿**               | 互斥锁 `redisLockUtil.tryLock` + double-check，只有一个线程查库重建                                                       |
| **防穿透**               | 查库结果为空时写空值标记 `""`（TTL 30s），下次命中直接返回空列表                                                                      |
| **防雪崩**               | `randomTtl()`：5 分钟 + 随机 0\~60 秒偏移，打散过期时间                                                                    |
| **降级兜底**              | 抢锁失败重试 3 次仍无缓存 → 直接查库返回（不写缓存）；缓存写入失败 catch 后只记日志不影响返回                                                       |
| **searchCount=false** | `queryHotFromDb` 里 `new Page<>(1, limit, false)` 省掉无意义的 COUNT 查询                                            |

### 10. 秒杀商品列表：getSeckillProducts

`GET /api/products/seckill` 返回已配置秒杀价且上架的商品，按秒杀开始时间升序，最多 50 条。

```java
qw.isNotNull(Product::getSeckillPrice)
  .eq(Product::getStatus, 1)
  .orderByAsc(Product::getSeckillStart)
  .last("LIMIT 50");
```

**为什么不做缓存？** 代码注释里写得很清楚：秒杀的真实库存在 Redis（`citygo:seckill:stock:*`），DB 的 `seckill_stock` 只在取消回补等低频场景变化；而秒杀配置（商家改价/改时间）需要**近实时生效**，缓存反而引入不一致。单次 `isNotNull + LIMIT 50` 的查询成本很低，直接查库即可。

**路由不冲突**：`/api/products/seckill` 和 `/api/products/{id}` 不会冲突——Spring MVC 路由匹配时**字面量路径优先于路径变量**，`/seckill` 优先匹配到 `seckillList()` 方法。

### 11. 分类模块为什么只有查询接口？（先想清楚：分类是谁的数据）

**事实**：全项目搜索不到任何 `categoryMapper.insert/updateById/delete` 写操作，分类只有 `listEnabledCategories()` 一个查询接口；分类数据全部来自 Flyway `V3__init_categories.sql` 预置的 6 个一级分类。

**本质**：商品/店铺是**商家私有数据**（商家随意 CRUD，配合两级归属校验），而分类是**全平台共享的字典/枚举数据**——所有用户、所有商品、所有页面都在引用它：

| 数据      | 归属   | 谁能写                   |
| ------- | ---- | --------------------- |
| 商品 / 店铺 | 商家私有 | 归属校验通过的商家             |
| 分类      | 平台全局 | **只有平台运营**（当前用迁移脚本维护） |

**为什么不能开放写？** 分类一旦开放给任意商家/用户，就会：重复分类（卖烤串的建"烤串"、卖烧烤的建"烧烤"）、恶意刷脏分类、牵连所有用户看到的分类页——**全局数据必须把写权限收在一个口子**。

**伏笔已埋**：项目角色体系已就绪却没用到——`Role` 种子数据有 `CODE_ADMIN` 常量（见文件索引）、`user_role` 表维护用户-角色多对多绑定、登录态 Redis 值存的是 `userId:roleCodes`。未来的平台管理后台只需校验 `ADMIN` 角色即可开放分类管理接口（POST `/api/admin/categories` → ADMIN 校验 → 防重名校验 → insert）。

> 顺带注意两个细节：① 种子数据用 `INSERT IGNORE` + 固定主键 1-6，保证迁移脚本**可重复执行**不报主键冲突；② `CategoryVO` 只有 4 个字段（id/名称/图标/sort），`parentId/status/deleted` 全不外露——`parentId` 字段本身是**层级设计伏笔**（0=一级），当前只用了一层。

## e. 面试真题

**Q1：MyBatis-Plus 的分页是怎么配置的？**

答：注册 `MybatisPlusInterceptor` 并加入 `PaginationInnerInterceptor(DbType.MYSQL)`，查询时传 `new Page<>(pageNum, pageSize)` 给 `selectPage`。注意 MP 3.5.9+ 两个变化：DbType 用枚举写法，且分页插件拆到了 `mybatis-plus-jsqlparser` 依赖，不引会 ClassNotFound。

> 考官想考察：是否真配过 MP 分页，以及对版本演进（插件拆模块）的了解。

**Q2：为什么分页返回 PageVO 而不是直接返回 MP 的 Page 对象？**

答：Page 是 MyBatis-Plus 内部实现，直接返回会把 MP 依赖和内部字段（如 searchCount、optimizeCountSql）暴露给前端，也难序列化。PageVO 只保留 records/total/pageNum/pageSize 四个稳定字段，与 MP 解耦，前端契约稳定。

> 考官想考察：接口契约设计意识——对外不暴露内部实现。

**Q3：商品列表接口为什么要把 stock 置 null？**

答：库存是商家经营数据，属于敏感信息，用户端不需要也不应看到（否则能被竞对爬库存、猜经营状况）。所以公开接口 `pagePublic`/`getPublicDetail` 组装完 VO 后 `vo.setStock(null)`，商家侧接口才返回库存。

> 考官想考察：对"公开/内部接口脱敏"的安全意识。

**Q4：列表接口的排序字段为什么要白名单映射？**

答：防 SQL 注入。如果直接把用户传的 sort 拼进 SQL（如 `ORDER BY ${sort}`），攻击者能注入任意 SQL。CityGo 用 switch 把 sort 白名单映射到 `orderByDesc(Product::getSales)` 这类方法引用，未知值走 default，绝不拼接用户输入。

> 考官想考察：对 SQL 注入防范的落地，而非只会说"用预编译"。

**Q5：什么是 N+1 查询？你们怎么优化？**

答：N+1 指查 N 条记录后，每条再单独查一次关联数据（如商品补分类名），总共 N+1 次查询。优化是批量预取：先收集去重的 categoryId，`selectByIds` 一次取回转成 Map，组装时查表。CityGo 的 `loadCategoryNames`、评价列表补店铺名/昵称、搜索同步补店铺名都是这个套路。

> 考官想考察：是否理解 N+1 并能给出"批量查询 + Map 映射"的标准解法。

**Q6：商家查"我的商品"怎么防止看到别人的商品？**

答：不指定 shopId 时，先查当前商家名下所有店铺 id，再 `qw.in(Product::getShopId, myShopIds)` 限定范围；指定 shopId 时先 `requireOwnedShop` 做归属校验。商品写操作则通过 `requireOwnedProduct`（查商品 → 校验店铺归属）防越权。

> 考官想考察：数据越权防护——"查询范围收敛到自己的数据"。

**Q7：热门商品接口和秒杀商品列表，为什么一个用缓存、一个不用？**

答：热门商品是**读多写少**的典型场景——销量排名变化慢、请求频率高，用缓存挡在数据库前面收益巨大，所以做了完整的手写缓存三防（击穿/穿透/雪崩，详见 09 篇）。秒杀商品列表则刚好相反——秒杀配置（商家改价/改时间）需要**近实时生效**，缓存反而引入不一致；且单次 `isNotNull + LIMIT 50` 的查询成本极低，直接查库即可。这体现了"缓存不是万能药，要根据数据新鲜度要求和查询成本决定是否缓存"的判断力。

> 考官想考察：是否理解缓存的使用前提——数据变化频率低、查询成本高才值得缓存；能否根据场景做不同决策而非一刀切。

**Q8：分类模块为什么只有查询接口，不开放创建分类？**

答：分类是**全平台共享的字典数据**（被所有用户/商品/页面引用），不同于商品/店铺这类商家私有数据，写权限必须收在平台运营手里。若开放给任意商家/用户写，会出现重复分类、恶意刷脏数据、牵连全局页面等问题。当前阶段分类由 Flyway 种子数据（`INSERT IGNORE` 固定主键，可重复执行）维护；未来由 ADMIN 角色的管理后台接管——项目中角色体系（`Role.CODE_ADMIN` + `user_role` 绑定表 + 登录态存 `roleCodes`）已就绪，属于刻意预留的伏笔。

> 考官想考察：对"私有数据 vs 全局字典数据"的权限边界意识，以及一眼看出角色体系是为管理端预留的设计直觉。

## f. 开发实战扩展

1. **SKU 规格**：真实商品有 SKU（颜色/尺码），product 表会拆成 SPU + SKU 两级，库存和价格挂在 SKU 上，CityGo 是单规格简化。
2. **库存扣减独立成服务**：高并发下库存扣减会抽成独立的库存服务（Redis + 异步落库），商品服务只做信息展示。
3. **图片存对象存储**：cover\_image/images 存 URL，生产接 OSS/COS + CDN，不存本地。
4. **分类树缓存**：分类层级数据变化少，生产会整树缓存进 Redis，而不是每次查库。
