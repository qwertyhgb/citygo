# 12 优惠券：领券并发三件套与核销幂等

> 本篇对应 CityGo 优惠券域：券模板、用户券、领券、用券、退券的完整链路。优惠券是"高并发 + 强一致性"叠加的典型场景——领券要防超发、防重复领取，用券要防他人券、防超门槛、防重复核销。学完本篇，你要能回答：并发领券怎么不多发、不少发、不重发，以及一张券从领取到核销到退回的完整状态机。

---

## a. 这个模块是干嘛的

CityGo 的优惠券分**平台券**（全场可用）和**商家券**（指定店铺可用），商家发券引流、用户领券下单、订单取消退券，构成一个完整的营销闭环。这个模块的核心难点不在业务本身，而在**并发正确性**：

1. **领券防超发**：发行 1000 张绝不能发出 1001 张；
2. **领券防重复**：每人限领 `per_user_limit` 张（默认 1，也支持多张），高并发下不能超领；
3. **用券防作弊**：不能用别人的券、不能用过期券、不能突破满减门槛；
4. **核销与退券幂等**：并发下重复核销/重复退券不能出错。

一句话：这一篇讲的是**怎么用"业务校验 + Redis 分布式锁 + 数据库条件更新"三件套，把优惠券的并发正确性做扎实**。

## c. 先懂概念

- **券模板 vs 用户券**：`coupon` 是"券的说明书"（发行多少、满多少减多少），`user_coupon` 是"用户手里的一张券实例"（谁领的、用没用、绑了哪个订单）。一个模板对应多张用户券。
- **条件更新（原子更新）**：`UPDATE ... WHERE status=1` 这类带状态条件的 SQL，是数据库原子操作，行锁保证同一时刻只有一个请求能改成功，返回 0 行即"已被别人抢先"。这是防超发、幂等核销、退券的共同武器。
- **分布式锁串行化**：业务查重（"你还没领过"）只能防 99% 的场景，两个请求"同时查都没查到、同时插"时会双双插入。CityGo 用"用户-券"维度的 Redis 分布式锁把同一用户的并发领券请求**串行化**，从根源上杜绝瞬时超领。（通用兜底方案还有数据库唯一索引——插入即抛 `DuplicateKeyException`；CityGo 初版用的就是它，V6 为支持"限领多张"改为普通索引后，防并发职责移交给了分布式锁。）
- **惰性过期**：不在后台定时任务里逐张标记过期券，而是用户**查询时**顺手把已过期的券一次性标记为过期状态，省掉定时扫表的成本。
- **HALF_UP**：四舍五入的舍入模式。金额计算必须显式指定，否则 `BigDecimal.divide` 遇到除不尽会抛 `ArithmeticException`。

## d. 逐个详解

### d1. 数据模型：coupon 与 user_coupon 的分工

`Coupon` 实体承载券模板的静态信息，几个关键字段的设计意图：

- `type`：1 满减券、2 折扣券，两者用**互斥字段**表达——`discountAmount`（满减金额）只对 type=1 有意义，`discountRate`（折扣率，85 表示 8.5 折）只对 type=2 有意义；
- `totalCount`（发行总量）与 `receivedCount`（已领取数）：**已领取数是领券时累加的**，配合条件更新实现防超发；
- `scope`：1 平台券 / 2 商家券，商家券必须配合 `shopId` 限定使用店铺。

`UserCoupon` 是券实例，`status` 三态（1 未使用 / 2 已使用 / 3 已过期）是核销与退券状态机的核心；`orderId` 在核销时关联订单、退券时清空；`expireTime` **冗余自模板 `valid_end`**——注释里点明了冗余目的：便于惰性过期与查询，不用每次 join 模板表。

**坑在哪**：`expireTime` 是冗余字段，意味着它和 `coupon.valid_end` 存在两份数据，如果模板改了有效期，已领的券不会自动跟着变。这是"冗余换查询效率"的经典取舍，面试要能讲出这个权衡。

### d2. V4 迁移：相对时间种子数据的技巧

`V4__init_coupons.sql` 插入两张平台券，有两个技巧值得学：

1. **`INSERT IGNORE` + 固定主键**：券 id 固定为 1、2，配合 `INSERT IGNORE`，脚本可重复执行——第一次插入生效，后续重复执行被主键冲突忽略，不会报错也不会重复插；
2. **相对时间**：`valid_start = DATE_SUB(NOW(), INTERVAL 1 DAY)`、`valid_end = DATE_ADD(NOW(), INTERVAL 1 YEAR)`，让这两张券"永远可用"，**避免迁移执行时刻固化**导致后启动的实例拿到过期券。

**坑在哪**：如果种子数据写死一个固定的 `2024-01-01 ~ 2024-12-31`，项目跑到 2026 年启动时，迁移插进去的券全是过期的，新手一测就懵。相对时间是迁移种子数据的最佳实践。

### d3. claim 领券：Redis 锁 + 条件更新 + 业务限领（支持限领多张）

`CouponServiceImpl.claim` 是本篇核心，采用"Redis 分布式锁 + 数据库条件更新 + 业务限领统计"的设计：

**0. Redis 分布式锁防瞬时并发击穿**：
进入领券前先获取用户-券维度的分布式锁：`redisLockUtil.tryLock("citygo:lock:coupon:claim:" + couponId + ":" + currentUserId, 5, token)`。
- **为什么需要分布式锁**：为了支持 `per_user_limit > 1`（如一人可领 2 张券），数据库去掉了死板的 `uk_user_coupon(user_id, coupon_id)` 唯一约束；引入细粒度分布式锁后，同一用户无论手速多快、并发多高，同一时刻领券请求全部串行化，**杜绝并发瞬时超领与幽灵领券**。

**前置校验（a-c）**：查券模板存在、有效期、状态可领。

**d. 业务限领统计**：
统计该用户已领取该券的总数 `userCouponMapper.selectCount(userId, couponId)`。若已领总数 `>= perUserLimit` 则抛 `COUPON_ALREADY_CLAIMED`。

**e. 超发控制（数据库条件更新）**：
```java
int rows = couponMapper.update(null, Wrappers.<Coupon>lambdaUpdate()
        .eq(Coupon::getId, couponId)
        .apply("received_count < total_count")
        .setSql("received_count = received_count + 1"));
if (rows == 0) throw new BizException(ErrorCode.COUPON_EXHAUSTED);
```
**为什么不能"先查再改"**：并发下两个请求同时读到 `received_count=999`（还剩 1 张），都判定可发，最终发出 1001 张。`UPDATE ... WHERE received_count < total_count` 是数据库原子语句，行锁保证同一时刻只有一次 +1 成功，返回 0 行即领完——这就是防超发的核心。

**f. 插入用户券**：
向 `user_coupon` 插入新券记录（status=1 未使用），并在 `finally` 块中通过 Lua 脚本原子释放分布式锁。

### d4. computeCouponDiscount：用券校验链与金额计算

下单时的用券校验在 `OrderServiceImpl.computeCouponDiscount`，是一条完整的校验链：

1. **防用他人券**：`userCoupon.getUserId().equals(userId)` 不符即拒；
2. **状态校验**：status 必须为 1（未使用）；
3. **过期校验**：expireTime 早于当前时间即拒；
4. **范围校验**：`scope==2` 的商家券必须 `coupon.getShopId().equals(orderShopId)`，否则 `COUPON_SCOPE_MISMATCH`；
5. **门槛校验**：`totalAmount < thresholdAmount` 即拒（`COUPON_THRESHOLD_NOT_MET`）。

金额计算分两种类型：

- **满减券**：`discount = coupon.getDiscountAmount().min(totalAmount)`——优惠不能超过订单总额；
- **折扣券**：`discount = totalAmount × (100 - rate) / 100`，`divide(100, 2, RoundingMode.HALF_UP)`——显式指定保留 2 位小数、四舍五入；
- **兜底**：最后 `return discount.min(totalAmount)`，保证支付金额不为负。

**坑在哪**：折扣计算里如果忘了 `divide(..., 2, RoundingMode.HALF_UP)` 的舍入参数，`BigDecimal` 除不尽时（如 33.33/100）会抛 `ArithmeticException`。金额计算必须显式指定精度和舍入模式。

### d5. useCoupon 核销幂等 + returnCoupons 退券

**核销（useCoupon）**：下单流程里订单插入后执行，SQL 逻辑是 `UPDATE user_coupon SET status=2, order_id=?, used_time=NOW() WHERE id=? AND user_id=? AND status=1`——**条件更新 `status=1` 保证幂等**：并发重复核销时，第二个请求的条件 `status=1` 不成立，返回 0 行，不会重复占用。这就是"核销幂等"的核心。

**退券（returnCoupons）**：取消订单时调用，先按 `order_id + status=2` 查出该订单核销过的券，再逐张 `UPDATE ... SET status=1, order_id=NULL, used_time=NULL WHERE id=? AND status=2`——条件更新 `status=2` 保证幂等：已退过的券返回 0 行，忽略即可。注释强调退券与回补库存在同一事务，保证一致性。

**为什么核销要在"订单插入后"**：`computeCouponDiscount` 只负责校验和算钱、**不写库**（注释明确），核销要拿到 `order.id` 才能写 `order_id` 关联，所以拆成两步——先算钱、订单落库后再核销。如果校验和核销合成一步，拿不到订单号就没法回填 `order_id`。

### d6. pageMy 惰性过期 + 批量关联防 N+1

`pageMy` 有两个细节：

1. **惰性过期**：查询前先执行一条 `UPDATE ... SET status=3 WHERE user_id=? AND status=1 AND expire_time < now`，把已过期未使用的券一次性标记为过期。**为什么不做定时任务**：券过期是"查询时顺手处理"就能搞定的，省掉定时扫表的成本和复杂度；
2. **批量关联**：查出用户券后，`distinct()` 收集所有 `couponId`，一次 `selectByIds` 拉回模板，`toMap` 组装，避免逐张查模板的 N+1。

## e. 面试真题

**Q1：并发领券怎么防止超发（多发）？**
结合 CityGo：`CouponServiceImpl.claim` 里用条件更新——`UPDATE coupon SET received_count = received_count + 1 WHERE id=? AND received_count < total_count`，返回 0 行即抛 `COUPON_EXHAUSTED`。数据库行锁保证同一时刻只有一个请求能 +1 成功。不能"先查再改"，因为并发下两个请求会读到同一剩余量、都判定可发。
考官想考察什么：是否理解"先查再改"的竞态，以及条件更新 `WHERE received_count < total_count` 作为原子防超发武器的原理。

**Q2：怎么防止重复领取同一张券？**
结合 CityGo：双重防线——①业务层限领统计：`selectCount(userId, couponId)` 统计该用户已领取总数，`>= perUserLimit` 即抛 `COUPON_ALREADY_CLAIMED`（支持一人限领多张）；②Redis 分布式锁：进入领券前 `tryLock("citygo:lock:coupon:claim:{couponId}:{userId}", 5, token)`，同一用户无论并发多高，同一时刻只有一个领券请求在执行，业务查重的"同时查都没查到"竞态窗口被锁彻底关闭。锁在 finally 中用 Lua 脚本原子释放（持有者校验，防误删他人锁）。
考官想考察什么：是否知道业务查重防不了"同时点击"，以及分布式锁串行化与唯一索引兜底两种方案各自的适用面（CityGo 因"限领多张"放弃了唯一索引，V6 迁移把 uk 改成了普通索引）。

**Q3：领券中途失败（售罄/限领超限/校验不过），已 +1 的发行量怎么办？**
结合 CityGo：领券全程在同一个 `@Transactional` 里，任何一步抛 `BizException` 都会让事务整体回滚——e 步的 `received_count + 1` 与"插入用户券"要么都成功、要么都撤销，不会出现"领券失败但发行量却少了"或"发行量没加但券发出去了"的脏数据。三件套分工：**分布式锁**（防并发超领）、**条件更新**（防超发）、**事务**（保证两者副作用联动一致）。
考官想考察什么：是否理解事务回滚如何把"条件更新 +1"与"插入用户券"两个动作的副作用绑定成一个原子单元。

**Q4：用券的校验链有哪些？为什么要这么多校验？**
结合 CityGo：`computeCouponDiscount` 依次校验——①防用他人券（userId 归属）、②状态未使用、③未过期、④商家券限定店铺（scope/shopId）、⑤满减门槛（thresholdAmount）。缺一环都可能被薅羊毛：不校验归属能拿别人券、不校验门槛能用 5 元券抵扣 3 元订单。
考官想考察什么：能否系统列出校验链，并说出每一环挡住的是哪类作弊/漏洞。

**Q5：核销怎么保证幂等？重复核销会怎样？**
结合 CityGo：`useCoupon` 用条件更新 `UPDATE ... SET status=2, order_id=?, used_time=NOW() WHERE id=? AND user_id=? AND status=1`。并发重复核销时，第二个请求的 `status=1` 条件不成立，返回 0 行，不会重复占用——这就是幂等。退券同理，`returnCoupons` 用 `WHERE status=2` 条件更新，重复退券返回 0 行忽略。
考官想考察什么：是否理解"条件更新 + 状态字段"是幂等的通用实现，以及核销、退券两个方向的对称性。

**Q6：取消订单怎么退券？**
结合 CityGo：`cancelInternal` 里调 `returnCoupons(orderId)`——先按 `order_id + status=2` 查出该订单核销过的券，再逐张条件更新 `status=2→1` 并清空 `order_id/used_time`。退券与回补库存在同一事务，保证一致性；条件更新保证幂等，已退过的券 0 行忽略。
考官想考察什么：能否完整描述"查已核销券 → 条件更新退回"的流程，以及退券与订单取消的事务一致性。

**Q7：折扣券的金额怎么算？为什么用 HALF_UP？**
结合 CityGo：满减券 `discount = min(满减金额, totalAmount)`，折扣券 `discount = totalAmount × (100 - rate) / 100`，如 85 折就是 `totalAmount × 15 / 100`，用 `divide(100, 2, RoundingMode.HALF_UP)` 保留 2 位小数四舍五入。必须显式指定舍入模式，否则 `BigDecimal` 除不尽会抛 `ArithmeticException`。最后 `discount.min(totalAmount)` 兜底，保证支付金额不为负。
考官想考察什么：是否掌握 `BigDecimal` 精度与舍入模式，以及优惠金额不能超过订单总额的兜底意识。

## f. 开发实战扩展

- **用 Redis 限流 + 缓存挡领券洪峰**：CityGo 的领券直接打 DB，生产大促时会把"发行剩余量"预热到 Redis，用 Redis `DECR` 预扣 + DB 条件更新兜底（与 11 篇秒杀同款思路），避免海量请求抢数据库行锁。
- **核销幂等升级为幂等表**：条件更新已能覆盖核销幂等，但生产对"重复扣券"更严谨的做法是引入**独立的核销流水表**（唯一索引 order_id+coupon_id），让每一次核销动作可追溯、可对账。
- **券过期用延迟消息**：惰性过期省事但不够实时，生产对"过期券回收""过期提醒"会用 **RabbitMQ TTL+死信队列**（CityGo 已有该基础设施）或 RocketMQ 定时消息，在券到期时刻触发处理。
- **防刷升级**：唯一索引只能防"同一用户重复领"，防不了"注册 N 个小号批量领"，生产会叠加**设备指纹、IP 限频、风控模型**等手段，学习项目不做。
