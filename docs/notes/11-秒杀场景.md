# 11 秒杀场景：Redis 预扣 + MQ 异步 + DB 兜底

> 本篇是 CityGo 的高并发重点篇。秒杀是"Redis + RabbitMQ + 数据库条件更新 + 限流"四大件合力的终极考场：它把前面 08（订单）、09（Redis）、10（MQ）三篇的知识全部串了起来。学完本篇，你要能完整画出秒杀链路，并回答超卖、重复购买、库存竞争、高并发四大面试问。

---

## a. 这个模块是干嘛的

秒杀（如"1 元抢购""限量 100 件"）的特点是**瞬时流量极高 + 库存极稀缺 + 每人限购一件**。如果直接复用普通下单链路，海量请求会在同一瞬间涌入 MySQL 抢行锁，数据库瞬间被打爆。CityGo 的秒杀场景用三层设计解决：

1. **Redis 预扣**：把"一人一单"和"库存扣减"这两个最高频的动作放到 Redis 内存里原子完成，扛住 99% 的并发；
2. **MQ 异步削峰**：抢到资格的请求才发消息，由消费者慢慢落库创建订单，前端立即返回"抢购成功，订单创建中"；
3. **DB 兜底**：消费者落库时再做一次"一人一单复查 + 条件更新扣库存"，兜住 Redis 异常等极端情况。

一句话：这一篇讲的是**怎么用"内存原子操作 + 消息队列削峰 + 数据库兜底"三层结构，把瞬时洪峰消化掉**。

## c. 先懂概念

- **库存预扣**：先在高性能存储（Redis）里把库存"口头扣掉"，真正的落库放到异步或最终处理。好处是把高并发流量挡在数据库之外。
- **一人一单（限购）**：同一用户对同一秒杀商品只能成功抢一次。核心是"去重"，但要扛住并发下的重复请求。
- **原子操作**：Redis 的 `SETNX`（set if not exists）、`DECR`（自减）都是单条命令原子执行，多线程并发下不会出现"读到旧值再改"的竞态。
- **削峰**：把瞬间洪峰通过消息队列摊平成消费者能处理的匀速流量，核心链路先返回成功，落库异步完成。
- **兜底**：每一层都可能失效（Redis 宕机、消息丢失、极端并发穿透），所以要在更底层（数据库）再设一道最终防线。

## d. 逐个详解

### d1. V5 迁移：秒杀需要哪些数据支撑

`V5__seckill_fields.sql` 只做了两类改动：

- `product` 表加 4 个秒杀字段：`seckill_price`（秒杀价）、`seckill_stock`（秒杀库存）、`seckill_start`、`seckill_end`，全部 `NULL`——**NULL 表示不参与秒杀**，用一个字段的可空性表达"是否秒杀商品"，省掉一个布尔开关；
- `orders` 表加 `source` 字段（1 普通 2 秒杀）。

**为什么必须加 `source`**：注释里写了两条理由——①秒杀订单取消时要回补的是 `seckill_stock` 和 Redis 预扣库存，而不是普通库存；②秒杀消费者做一人一单 DB 复查时，要区分普通订单与秒杀订单（只查 `source=2`）。一个字段，决定了后续所有"库存扣减/回补路径"和"去重策略"的分叉。

### d2. configSeckill：商家怎么开启一场秒杀

`SeckillServiceImpl.configSeckill` 是商家配置秒杀的入口，流程清晰：

1. **时间合法性**：结束时间必须晚于开始时间，否则 `BAD_REQUEST`；
2. **商家身份 + 商品存在性**校验；
3. **店铺归属校验**：必须是当前商家所属店铺下的商品（沿用普通商品的 `requireOwnedShop` 逻辑）；
4. **更新 DB**：把秒杀价/库存/起止时间写进 product；
5. **覆盖 Redis 预扣库存**：`set(KEY_SECKILL_STOCK_PREFIX + productId, String.valueOf(request.getSeckillStock()))`——注释强调配置变更后**直接 set 覆盖**，以最新配置为准、即时生效；
6. **失效缓存 + 事务提交后同步 ES**。

**坑在哪**：第 5 步的"覆盖"是刻意的设计选择——如果配置期间已有用户在抢，直接覆盖 Redis 库存会重置计数。但学习场景下配置秒杀通常在活动开始前完成，注释也点明了"以最新配置为准"的取舍。

### d3. seckill 四步抢购：SeckillServiceImpl.seckill 走读

这是全篇最核心的方法，按注释标记的 a→f 六步走读：

**a. 查商品 + 完整性校验**：商品必须存在，且 `status=1`（上架）、四个秒杀字段都非 NULL，否则 `SELL_NOT_AVAILABLE`——防止对未开启秒杀的普通商品发起抢购。

**b. 时段校验**：`now` 在 `seckillStart` 之前抛 `SELL_NOT_STARTED`，在 `seckillEnd` 之后抛 `SELL_ENDED`。**为什么**：不在活动时间窗口内的请求必须被立刻拦截，避免非活动时间扣减库存。

**c. 一人一单（Redis SETNX）**：`setIfAbsent(userKey, "1", ttl)`，userKey = `citygo:seckill:user:{productId}:{userId}`，TTL 设为**到秒杀活动结束的剩余时间**。SETNX 失败（返回 false）说明已抢过，抛 `SELL_REPEAT`。

- **为什么用 Redis 而不是查 DB**：查 DB 做去重在并发下会穿透、且压力全压在数据库上；Redis SETNX 是原子操作，内存级去重，扛得住高并发。
- **TTL 为什么是"到活动结束剩余时间"**：活动一结束，这个去重标记就该自然过期，不占用内存；下一个活动周期用户又能重新抢。

**d. 预扣库存（Redis DECR）**：`decrement(stockKey)` 原子自减。若结果 `< 0`，说明扣超了，**必须 INCR 回滚 + delete userKey 释放限购标记**，然后抛 `SELL_OUT`。

- **为什么 DECR 而不是"查库存再减"**：DECR 是单条原子命令，内存里瞬间完成超卖控制；如果先 `get` 再 `set`，并发下两个请求会读到同一个剩余值，双双放行导致超卖。
- **负值回滚的两个动作**：`increment(stockKey)` 把扣成负数的库存加回来，`delete(userKey)` 把刚才误占的限购标记删掉，让用户还能重试。两个动作缺一不可——只回滚库存不回滚标记，用户被"已抢过"卡死；只删标记不回滚库存，库存凭空少一个。

**e. 发 MQ 异步下单**：`convertAndSend("citygo.seckill.order.exchange", "seckill.order", new SeckillMessage(userId, productId))`，然后方法结束。

**f. 返回成功**：控制器返回 `Result.success("抢购成功，订单创建中")`——注意是"订单创建中"而不是"下单成功"，因为订单此时还没落库，由消费者异步创建。

### d4. SeckillOrderConsumer：DB 兜底 + 异步落库

消费者 `onSeckillOrder` 是最终防线，按 a→d 四步：

**a. DB 一人一单复查**：`hasPurchasedInDB(userId, productId)` 查该用户是否已有该商品的非取消秒杀订单。Redis 防了 99% 并发，DB 复查兜住极端情况（Redis 宕机重启、消息重复投递等）。

- 复查逻辑：先查 `userId + source=2 + status != CANCELLED` 的秒杀订单，再查这些订单的明细里有没有该 `productId`——因为订单不直接存商品，要透过 order_item 关联。

**b. 商品状态 + 时段再校验**：防下架/过期/配置变更。若商品已下架或活动已结束，**Redis INCR 回补预扣库存**，丢弃消息。

**c. DB 秒杀库存条件更新兜底**：`productMapper.deductSeckillStock(productId, 1)`，SQL 是 `UPDATE product SET seckill_stock = seckill_stock - 1 WHERE id = ? AND seckill_stock >= 1`。**0 行说明 DB 真实库存已售罄**（Redis 预扣与 DB 真实库存出现偏差），Redis INCR 回补 + 丢弃。

**d. 创建订单**：雪花单号 `IdWorker.getIdStr()`、`source=2`、状态待支付、金额用秒杀价、地址快照（无地址则置空并记 WARN，支持"先抢后补地址"）、插入明细快照、销量累加、**发超时 TTL 延迟消息**（复用普通订单的 30 分钟超时取消机制）、缓存失效 + ES 同步。

**为什么要"先回补 Redis 再丢弃"**：b/c 两步的失败都说明"Redis 预扣了但订单没建成"，如果不回补，Redis 库存会凭空少一个，最终导致"有货却抢不到"。

### d5. 双层防超卖：Redis 闸门 + DB 条件更新

这是秒杀防超卖的完整闭环，两层职责不同：

| 层 | 位置 | 机制 | 作用 |
|----|------|------|------|
| 第一层（流量闸门） | `SeckillServiceImpl.seckill` | Redis `DECR` 原子预扣 | 在内存里挡住 99% 的超卖，DB 零压力 |
| 第二层（最终兜底） | `SeckillOrderConsumer` | `UPDATE ... WHERE seckill_stock >= 1` 条件更新 | 兜住 Redis 与 DB 库存不一致、消息重复等极端情况，0 行即拒绝 |

两层都用的是同一个思想——**原子条件更新**，而不是"先查再改"。Redis DECR 的原子性来自 Redis 单线程命令；DB 条件更新的原子性来自数据库行锁。这个"防超卖"思想在 08 篇普通下单的 `deductStock` 里已经出现过，秒杀是它的高并发版本。

### d6. 秒杀订单取消回补：与普通订单的差异

取消回补在 `OrderServiceImpl.cancelInternal` 里，按 `source` 分叉：

```java
boolean isSeckill = OrderSource.SECKILL.getCode() == order.getSource();
// isSeckill 时：restoreSeckillStock(seckill_stock 加回 + 销量扣回) + Redis INCR citygo:seckill:stock:{productId}
// 普通时：restoreStock(普通库存加回 + 销量扣回)
```

**关键设计——一人一单的 Redis key 不删除**：注释明确说明，取消秒杀订单后 `citygo:seckill:user:{productId}:{userId}` **保留不删**，防止用户取消后再抢，符合"取消后本轮秒杀不可再抢"的业务惯例。这是秒杀与普通下单的一个微妙差异：普通订单取消后用户可以重新下单，秒杀取消后本轮不能再抢。

### d7. 秒杀与普通下单的异同对比

| 维度 | 普通下单（OrderServiceImpl.create） | 秒杀下单（seckill + SeckillOrderConsumer） |
|------|-------------------------------------|------------------------------------------|
| 库存扣减位置 | 同步在 DB：`deductStock` 条件更新 | 先在 Redis `DECR` 预扣，DB 由消费者条件更新兜底 |
| 是否异步 | 主链路同步完成落库 | Redis 预扣后发 MQ，订单异步创建 |
| 用户感知 | 同步返回完整订单 | 立即返回"订单创建中"，订单稍后生成 |
| 去重机制 | 无（可重复下单） | SETNX 一人一单 + DB 复查双层 |
| 库存字段 | 普通 `stock` | 独立 `seckill_stock`，与普通库存隔离 |
| 订单标记 | `source=1` | `source=2`，决定取消回补路径 |
| 取消后能否再买 | 可以 | 本轮不可再抢（一人一单 key 不删） |

**为什么秒杀库存要独立**：秒杀库存是"活动库存"，普通库存是"日常库存"，两者隔离才能保证"秒杀 100 件"不影响日常售卖，反之亦然。

## e. 面试真题

**Q1：秒杀的整体架构怎么设计？为什么这么分层？**
结合 CityGo：三层——①Redis 预扣（`SeckillServiceImpl.seckill` 里 SETNX 去重 + DECR 扣库存），扛住 99% 并发；②MQ 异步削峰（发 `seckill.order` 消息，前端立即返回"订单创建中"）；③DB 兜底（`SeckillOrderConsumer` 复查 + 条件更新扣库存后落库）。分层的核心思想是"让最扛得住的层扛住洪峰，数据库只在最后一刻被访问"。
考官想考察什么：能否画出完整链路，并讲清每一层解决什么问题、为什么要分层而不是让数据库直面流量。

**Q2：怎么防止超卖？**
结合 CityGo：双层防超卖。第一层 Redis `DECR` 原子预扣，`remain < 0` 时 INCR 回滚 + 抛 `SELL_OUT`；第二层消费者落库时 `deductSeckillStock` 用 `UPDATE ... WHERE seckill_stock >= 1` 条件更新，0 行说明 DB 已售罄、回补 Redis 并丢弃。两层都是"原子条件更新"而非"先查再改"，因为先查再改在并发下会读到同一旧值、双双放行。
考官想考察什么：是否理解"先查再改"的竞态问题，以及原子条件更新（Redis DECR / DB WHERE 条件）作为防超卖武器的原理。

**Q3：怎么防止同一用户重复购买？**
结合 CityGo：双层去重。第一层 Redis `SETNX`（`setIfAbsent(userKey, "1", ttl)`），userKey = `citygo:seckill:user:{productId}:{userId}`，TTL 设到活动结束剩余时间，失败抛 `SELL_REPEAT`；第二层消费者 `hasPurchasedInDB` 复查——查该用户 `source=2 且 status != CANCELLED` 的秒杀订单明细里是否含该商品，有则丢弃消息。Redis 防 99% 并发，DB 复查兜住 Redis 异常。
考官想考察什么：是否知道"限购去重"同样要分两层，以及 DB 复查要排除已取消订单、透过明细关联商品。

**Q4：高并发下库存竞争怎么解决？**
结合 CityGo：把库存竞争从数据库挪到 Redis——`DECR` 是 Redis 单线程执行的原子命令，内存里瞬间完成扣减，天然串行化，不产生数据库行锁竞争；只有抢到资格的请求才发 MQ 落库，数据库行锁压力被削峰摊平。核心是"把竞争最激烈的操作放到最快的存储上"。
考官想考察什么：能否对比"DB 行锁竞争"与"Redis 原子操作"的性能差异，理解秒杀为什么不能让数据库直接扛并发。

**Q5：秒杀下单为什么不能直接复用普通下单链路？**
结合 CityGo：普通下单是同步链路，下单 10 步全在数据库事务里完成，秒杀瞬间上万请求会同时抢数据库行锁，数据库直接打挂。秒杀改成"Redis 预扣 → MQ 异步 → 消费者落库"，主链路只做内存操作 + 发消息，立即返回"订单创建中"，订单由消费者慢慢创建，把同步洪峰变成异步队列。
考官想考察什么：是否理解"同步落库"在高并发下的瓶颈，以及 MQ 削峰的价值。

**Q6：秒杀订单超时未支付，库存怎么回补？一人一单标记为什么不删？**
结合 CityGo：秒杀订单也会发 30 分钟超时 TTL 延迟消息，超时后 `OrderTimeoutConsumer` 走 `cancelInternal`，按 `source=2` 分叉——`restoreSeckillStock`（seckill_stock 加回 + 销量扣回）+ Redis `INCR citygo:seckill:stock:{productId}`。但一人一单的 `citygo:seckill:user:{productId}:{userId}` **不删除**，防止用户取消后再抢，符合"取消后本轮秒杀不可再抢"的业务惯例。
考官想考察什么：是否注意到秒杀取消回补要"双写"（DB + Redis），以及"不删限购标记"背后的业务约束。

**Q7：秒杀接口为什么要限流？怎么限？**
结合 CityGo：`SeckillController` 的抢购接口标了 `@RateLimit(limit=10, windowSeconds=1)`，1 秒最多 10 次请求，防止恶意刷接口和极端突发流量。限流在 Redis 预扣之前——先把明显的刷子挡在门口，再让正常流量走 SETNX/DECR，否则 SETNX 和 DECR 也会被恶意流量打满。
考官想考察什么：是否理解限流在整个秒杀链路的"第一道闸门"位置，以及它与去重、库存扣减的分工。

**Q8：秒杀里如果消息重复投递，会不会重复创建订单？**
结合 CityGo：会依赖消费者的幂等兜底——`onSeckillOrder` 第一步就 `hasPurchasedInDB` 复查，已存在有效秒杀订单则丢弃消息；即便 DB 复查因并发恰好同时通过，`deductSeckillStock` 的条件更新在库存层面还能兜住一部分。真正的重复投递在"创建订单"这步没有唯一索引约束，学习项目靠复查 + 条件更新尽力保证，生产会再加订单号唯一索引或幂等表。
考官想考察什么：能否区分"尽力幂等"与"强幂等"，并指出学习项目在重复投递场景下的兜底边界。

## f. 开发实战扩展

- **库存预扣的精确化**：CityGo 的 Redis 预扣是"扣了再异步落库"，极端情况下 Redis 和 DB 库存会短暂不一致，靠消费者兜底回补。生产常用 **Lua 脚本把"查库存 + 扣库存"合并成一条原子命令**，或在预扣成功后就写一个"预扣流水"便于对账。
- **消息可靠性补齐**：`seckill` 里 `convertAndSend` 发送失败没有补偿（注释里写明学习项目不做本地消息表），生产必须加**本地消息表 + 定时补偿**，否则"Redis 扣了库存但消息没发出去"会导致用户抢到却无订单。
- **限购去重的存储升级**：Redis SETNX 是简单去重，生产对"一人一单"可能用 **Lua 脚本原子执行"判断 + 标记 + 扣库存"**，把多次网络往返合并成一次，进一步提升吞吐并减少中间态不一致窗口。
- **前端防抖与验证码**：接口层限流只是后端防线，生产秒杀页还会加**按钮防抖、滑块/图形验证码、答题**等手段，在客户端先过滤掉机器刷单流量。
