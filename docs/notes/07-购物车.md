# 07 · 购物车

> 本篇覆盖：Redis Hash 存储设计（key / field / value、TTL 7 天刷新）、StringRedisTemplate 零序列化坑、失效商品 offSale 标记、与 MySQL 存储的取舍。

## a. 这个模块是干嘛的

购物车是用户下单前的"临时暂存区"。CityGo 把购物车存进 Redis 而不是 MySQL：key 是 `citygo:cart:{userId}`（Hash 类型），field 是商品 ID，value 是数量。为什么用 Redis？因为购物车是高频读写、生命周期短（可丢）的临时数据，Redis 内存操作快，还能天然设置 7 天过期自动清理，不用写定时任务。这一篇讲 Redis 存储结构设计的取舍，以及 StringRedisTemplate 的一个经典坑。

## c. 先懂概念

1. **Redis Hash**：一个 key 下存多组 field-value，适合"一个用户多个商品条目"这种场景，天然映射购物车。
2. **StringRedisTemplate**：只操作 String 的 RedisTemplate，key/value 都是字符串，**零自定义序列化**，避免 JDK 序列化的二进制不可读问题。
3. **TTL 刷新**：每次写操作后重新 `expire`，让"活跃用户的购物车"持续续期，7 天不活跃才过期。
4. **offSale 失效标记**：商品被删/下架后，购物车里还残留该条目，查询时标记 `offSale=true` 而不是直接丢弃，让前端提示用户"该商品已失效"。
5. **可丢数据**：购物车允许丢失（Redis 重启、过期），不像订单必须持久化，这是选 Redis 的前提。

## d. 逐个详解

### 1. 存储设计：Redis Hash

`CartServiceImpl` 的注释把设计讲全了：

- **key** = `citygo:cart:{userId}`，类型 Redis Hash；
- **field** = 商品 ID 字符串，**value** = 数量字符串；
- **TTL 7 天**，每次写操作刷新过期时间。

选 Hash 而不是 String（`citygo:cart:{userId}:{productId}` 每个商品一个 key）的原因：Hash 天然把"一个用户的购物车"聚合成一个 key，方便 `entries()` 一次取全、`size()` 取商品种数、整体 `delete` 清空。

### 2. StringRedisTemplate 零序列化坑

`CartServiceImpl` 用 `StringRedisTemplate` 的 `opsForHash()`（`HashOperations<String, String, String>`），注释强调"零自定义序列化"。坑在哪：

- 如果用普通 `RedisTemplate`（默认 JDK 序列化），存进去的是二进制字节流，redis-cli 里看到的是 `\xAC\xED...`，不可读、不可跨语言、强绑定 Java 类结构；
- `StringRedisTemplate` 的 key/value 强制 String，存进去就是可读文本，排查方便；
- 代价是**自己负责字符串转换**：数量要 `String.valueOf(quantity)`、读取要 `Integer.parseInt(value)`、field 要 `String.valueOf(productId)`、取回要 `Long.valueOf(field)`。

`CartServiceImpl.addItem` 里 `hash.increment(key, String.valueOf(productId), quantity)`——increment 支持字符串 value 的原子累加，避免了"先读再加回写"的并发问题。

### 3. 核心方法走读

- `addItem(userId, productId, quantity)`：先 `requireOnSale`（商品存在且上架），`hash.increment` 原子累加数量，`refreshTtl`，返回 `hash.size()`（商品种数）。
- `updateItem`：quantity=0 表示删除该条目（`hash.delete`），否则校验商品后 `hash.put` 覆盖数量，`refreshTtl`。
- `removeItem` / `removeItems` / `clear`：删单条 / 删一批（下单后清已购）/ 清空。
- `viewCart(userId)`：`hash.entries(key)` 一次取全，批量 `selectByIds` 查商品，组装 VO 并计算 subtotal。

### 4. offSale 失效标记（viewCart 的精华）

`viewCart` 拿到 Hash entries 后，对每个商品 ID 查库组装：

- 商品查不到（逻辑删除后 selectById 不返回）→ `offSale=true`，只有 productId 和 quantity；
- 商品 status=0（下架）→ 保留 name/cover/price 但 `offSale=true`；
- 正常 → 填全信息，`offSale=false`；
- 有 price 则算 `subtotal = price × quantity`。

**为什么标记而不是直接删**：如果直接删，用户加购的商品一下架就"凭空消失"，体验很差；标记 offSale 让前端灰显并提示"该商品已失效，请删除"，由用户决定去留。这是电商购物车的通用交互。

### 5. 与 MySQL 存储的取舍（面试重点）

为什么不存 MySQL，要存 Redis：

| 维度 | Redis（本方案） | MySQL |
| --- | --- | --- |
| 读写性能 | 内存操作，毫秒级 | 磁盘 + 索引，较慢 |
| 数据生命周期 | 临时可丢，7 天 TTL 自动清理 | 持久化，需手动清理 |
| 并发 | 单线程 + 原子命令（increment） | 行锁/事务 |
| 一致性 | 弱（Redis 重启丢数据） | 强（ACID） |

选 Redis 的前提是**购物车是临时可丢数据**。什么时候必须用 MySQL？购物车要跨端同步（App/网页登录后都在）、要长期保留、要做营销分析时。真实美团/淘宝的购物车其实**主要存 MySQL + Redis 缓存加速**，因为购物车要跨设备、要长期保留、要参与推荐；纯 Redis 是学习项目的简化选择，面试要能讲出这个差异。

## e. 面试真题

**Q1：购物车为什么用 Redis Hash 而不是 MySQL？**

答：购物车是高频读写、生命周期短的临时数据，Redis 内存操作快，Hash 天然映射"一个用户多商品"，7 天 TTL 自动过期免清理，increment 原子累加免并发问题。前提是购物车允许丢失。如果要求跨端同步、长期保留，就该用 MySQL 存 + Redis 缓存加速。

> 考官想考察：是否理解"数据结构选型要匹配数据特性"，而非无脑 Redis。

**Q2：Redis Hash 在这里的 key/field/value 分别是什么？**

答：key = `citygo:cart:{userId}`，field = 商品 ID 字符串，value = 数量字符串。一个用户的所有购物车条目聚合成一个 Hash，方便 entries 一次取全、size 取种数、整体 delete 清空。

> 考官想考察：对 Redis 数据结构的实际使用，能否说清字段映射。

**Q3：StringRedisTemplate 和 RedisTemplate 有什么区别？为什么购物车用前者？**

答：RedisTemplate 默认用 JDK 序列化，值存成二进制字节流，redis-cli 里不可读、强绑定 Java 类结构；StringRedisTemplate 强制 key/value 为 String，存进去是可读文本，零自定义序列化，便于排查。代价是数量/ID 要自己 String 互转。购物车场景数据简单（都是字符串），用 StringRedisTemplate 更合适。

> 考官想考察：对 JDK 序列化 vs 字符串序列化的取舍，以及"零序列化"的具体含义。

**Q4：购物车的 TTL 为什么是 7 天，而且每次操作要刷新？**

答：购物车是临时数据，7 天不活跃自动过期清理，省掉手动清理逻辑。每次写操作后重新 expire，让活跃用户的购物车持续续期，避免"用户天天用但购物车突然过期"。

> 考官想考察：对 TTL 滑动续期（活跃保活）的理解。

**Q5：商品下架了，购物车里的条目怎么办？**

答：不直接删，查询时标记 `offSale=true` 并保留名称/价格，前端灰显提示"商品已失效"。如果直接删，用户加购的商品一下架就凭空消失，体验差。正常商品 `offSale=false` 并算 subtotal。

> 考官想考察：对失效数据的柔性处理（标记而非硬删）的产品意识。

**Q6：加购数量累加用什么命令？为什么不用"先读再加回写"？**

答：用 Hash 的 `increment` 原子累加。如果先 `get` 再加再 `put`，并发下两个请求同时读到旧值，后写的会覆盖前一个（丢失更新）。increment 是 Redis 单线程内的原子操作，天然避免并发问题。

> 考官想考察：对 Redis 原子命令解决并发更新问题的理解。

## f. 开发实战扩展

1. **购物车落地 MySQL**：真实电商购物车通常 MySQL 持久化 + Redis 缓存，支持跨设备同步、长期保留、营销推荐。
2. **合并购物车**：登录前匿名购物车（存 Cookie/设备 ID）+ 登录后账号购物车，登录时合并，避免登录后购物车"变空"。
3. **价格实时校验**：这里 viewCart 时实时查价格算小计，生产会在结算时再校验一次价格/库存/上下架，防止加入后涨价或下架。
4. **限购与库存提示**：加购/查看时校验库存与限购数量，库存不足标记。
