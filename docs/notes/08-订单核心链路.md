# 08 · 订单核心链路（重点篇）

> 本篇覆盖：下单 10 步走读（地址归属 / 商品校验 / 同店铺 / 金额计算 / 雪花单号 / 快照 / CAS 扣库存 / 月销累加 / 清购物车 / 缓存失效）、防超卖（UPDATE WHERE stock>=? 为什么不能先查再改）、支付幂等（条件更新 + 已支付返回成功）、取消回补（含补充优化：取消后缓存失效 + ES 同步联动）、订单状态机（OrderStatus 枚举 + transition 条件更新）、404 防探测、@IdempotentSubmit AOP 防连点。

## a. 这个模块是干嘛的

订单是全项目最核心、最复杂的链路：用户提交地址和商品清单 → 校验 → 算钱 → 扣库存 → 生成订单 → 清购物车 → 发消息。这条链路串起了地址、商品、优惠券、库存、购物车、MQ、缓存、ES 七八个模块。订单系统的难点全在**并发正确性**：防超卖、支付幂等、取消回补、状态机流转，每一个都是面试必考。`OrderServiceImpl` 是 717 行的核心类，类注释自称"全项目最核心的类"，名副其实。

## c. 先懂概念

1. **CAS 扣库存（条件更新）**：`UPDATE product SET stock = stock - ? WHERE id = ? AND stock >= ?`，靠 `WHERE stock >= ?` 和数据库行锁保证不超卖，返回 0 行即库存不足。
2. **幂等**：同一操作执行多次结果一致。支付用"条件更新 + 已支付返回成功"实现幂等。
3. **状态机**：订单状态按固定路径流转（10→20→30→40→50），每次流转用 `WHERE status=from` 条件更新保证只成功一次。
4. **快照**：下单时把商品名/单价/收货信息固化进订单（02 篇已讲）。
5. **防探测**：无权访问的资源返回 404 而非 403，不暴露资源是否存在。
6. **AOP 防连点**：自定义注解 + 切面，用 Redis SETNX 在时间窗口内拦截重复提交。

## d. 逐个详解

### 1. 下单 10 步走读（OrderServiceImpl.create）

`create(OrderCreateRequest request, Long currentUserId)` 全程 `@Transactional`，按字母标了 a-m 步：

- **a. 地址校验**：`addressService.getById` 查地址，不存在抛 `ADDRESS_NOT_FOUND`，`!address.getUserId().equals(currentUserId)` 抛越权。防止用别人的地址下单。
- **b. 商品校验 + 同店铺**：批量 `selectByIds` 取商品，逐条校验存在（`PRODUCT_NOT_FOUND`）、上架（`PRODUCT_OFF_SHELF`）、同店铺（`ORDER_CROSS_SHOP`）。**一个订单只能属于一个店铺**，跨店直接拒。
- **c. 算商品总额**：`price × quantity` 累加，全 BigDecimal 运算。
- **c1. 用券计算优惠**：`computeCouponDiscount`（详见 12 篇）——券为空优惠 0，非空校验归属/状态/有效期/范围/门槛并算折扣。
- **d. 雪花单号**：`IdWorker.getIdStr()` 生成全局唯一字符串订单号。
- **e. 插入订单主表**：待支付、优惠=discount、实付=总额-优惠，收货信息从 address **快照拷贝**（省+市+区+详情拼接）。
- **e1. 核销用户券**：`useCoupon`（订单插入后才核销，因为要写 order_id）。
- **f. 插入明细快照**：商品名/图/单价/数量/小计全部快照。
- **g. CAS 扣库存**：`productMapper.deductStock`，返回 0 行抛 `INSUFFICIENT_STOCK`（整个事务回滚）。
- **h. 月销累加**：`shopMapper.addMonthlySales(shopId, 总数量)`。
- **i. 清购物车**：`cartService.removeItems(currentUserId, productIds)`。
- **k. 失效缓存**：`productService.evictProductDetail` + `evictHotProducts`（下单改了库存销量，详情/热门缓存会旧）。
- **l. 事务提交后发 MQ**：`publishOrderCreatedAfterCommit`（order.created + 超时 TTL 延迟消息）。
- **m. 事务提交后同步 ES**：`searchSync.afterCommit(...)` 同步商品销量库存。
- **j. 返回订单视图**。

**为什么 order.created 和 ES 同步都要 afterCommit**（l/m 步注释）：若事务回滚，订单实际未落库，此时发消息会让消费者处理不存在的订单（脏数据）；用 `TransactionSynchronizationManager.registerSynchronization` 的 `afterCommit` 保证"订单确实提交成功才通知下游"。

**为什么缓存失效在事务提交前**（k 步注释的诚实交代）：这里采用"下单成功即主动失效"的简化方案，极端并发下可能存在"缓存被旧数据回填"的短暂窗口，学习项目可接受；生产更严谨做法是事务提交后再失效。

### 2. 防超卖：为什么不能先查再改（核心）

`ProductMapper.deductStock`：

```sql
UPDATE product SET stock = stock - #{quantity}, sales = sales + #{quantity}
WHERE id = #{id} AND stock >= #{quantity}
```

注释讲透了：先查再改是"读改写"，并发下两个请求同时读到同一库存都判定充足，最终扣成负数（超卖）。而 `UPDATE ... WHERE stock >= ?` 是单条原子语句，数据库行锁保证同一时刻只有一个请求扣减成功，**返回 0 影响行数即库存不足**。

这是"乐观锁（条件更新）防超卖"的标准答案，面试高频。它其实也顺带累加了销量（`sales = sales + ?`），一步完成两件事。

### 3. 支付幂等（pay）

`pay(id, currentUserId)`：

1. `requireOwnerOrder` 归属校验（只能付自己的订单，404 防探测）；
2. **条件更新** `UPDATE orders SET status=20, paid_time=NOW() WHERE id=? AND status=10`；
3. rows == 0 时**再查一次**：若当前已是 20（已支付），说明是重复支付请求，**直接 return 视为成功**（幂等）；其他状态抛 `ORDER_STATUS_INVALID`；
4. 插入支付记录（payment_no 雪花、payMethod=3 模拟支付、status=2 成功）；
5. afterCommit 广播 `payment.success` 消息。

幂等的关键：条件更新保证"10→20 只发生一次"，重复请求撞到 rows=0，查出来已是 20 就返回成功，**不重复插入 payment**。唯一索引 `uk_payment_no` 是最后兜底。

### 4. 取消回补（cancelInternal）

`cancel`（用户取消）与 `cancelBySystem`（超时取消）共用 `cancelInternal`：

1. **状态条件更新** `WHERE status=10` → 置 60 + cancel_time + cancel_reason，0 行抛 `ORDER_STATUS_INVALID`（并发下已被处理）；
2. **回补库存**：按 `order.source` 区分——秒杀订单回补 `seckill_stock` 并 Redis INCR `citygo:seckill:stock:{productId}`；普通订单 `restoreStock`（库存加回、销量扣回）；
3. **月销回减**：`addMonthlySales(shopId, -总数量)`；
4. **退券**：`returnCoupons`（status=2→1 条件更新，清空 order_id/used_time，幂等）；
5. **缓存失效 + ES 同步**（补充优化）：`evictProductDetail` + `evictHotProducts` + `searchSync.afterCommit(syncProducts)`——取消会回补库存回减月销，商品详情/热门缓存和 ES 销量都要联动，与下单路径 k/m 步对称。

**为什么秒杀取消的 Redis 一人一单 key 不删**（注释）：防止用户取消后再抢，符合秒杀业务惯例（"取消后本轮秒杀不可再抢"）。

### 5. 订单状态机（OrderStatus + transition）

`OrderStatus` 枚举：10 待支付 / 20 已支付 / 30 已接单 / 40 配送中 / 50 已完成 / 60 已取消 / 70 退款中 / 80 已退款。流转表写在枚举注释里：10→20→30→40→50 主链路，10→60 取消，70/80 退款本期不实现。

商家流转统一走 `transition(orderId, currentUserId, from, to, targetUserId)`：

1. 查订单（404）；
2. 商家归属校验（当前用户必须是订单店铺的商家所有者，否则 403）；
3. **条件更新** `WHERE status=from` → 置 to，0 行抛 `ORDER_STATUS_INVALID`。

`accept`（20→30）、`deliver`（30→40）、`complete`（40→50，`set(condition, ...)` 条件置 completedTime）。**用条件更新保证并发下只允许唯一一次正确流转**——这是状态机的乐观锁实现。

### 6. 404 防探测（getDetail）

`getDetail` 的权限判断：`isOwner = order.getUserId().equals(currentUserId)`；`isMerchant = isMerchantOfShop(...)`。两者都不是时抛 `ORDER_NOT_FOUND`（404）而非 403。注释：**用 404 而非 403，避免暴露订单是否存在**（防订单号探测）。如果返回 403，攻击者能区分"订单存在但无权"和"订单不存在"。

`requireOwnerOrder` 也是：不存在或非本人统一 404。

### 7. @IdempotentSubmit AOP 防连点

`OrderController.create` 上标 `@IdempotentSubmit`。切面 `IdempotentSubmitAspect`：

1. 取请求头 `X-Request-Id`，无则直接放行（学习项目约定，生产可强制）；
2. key = `citygo:idempotent:{userId}:{requestId}`，`setIfAbsent(key, "1", ttl)` 首次放行设 TTL（默认 10 秒），非首次抛 `REPEAT_SUBMIT(409)`；
3. userId 从 SecurityContext 取，保证"同一请求号只对同一用户去重"。

**为什么下单要防连点**：用户双击提交会生成两笔订单、扣两次库存。`@IdempotentSubmit` 在接口层拦截"同一请求号 10 秒内重复提交"，与状态机/库存条件扣减形成双保险。但注意：它是"接口层去重"而非"业务幂等"，真正的幂等靠扣库存的条件更新。

## e. 面试真题

**Q1：你们怎么防超卖？**

答：CAS 条件更新。`UPDATE product SET stock = stock - ? WHERE id = ? AND stock >= ?`，返回 0 行即库存不足。不能先查再改：并发下两个请求同时读到同一库存都判定充足，会扣成负数。条件更新是单条原子语句，数据库行锁保证同时只有一个请求扣成功。

> 考官想考察：防超卖的标准答案（乐观锁条件更新），以及"为什么不能先查再改"。

**Q2：支付接口怎么做幂等？**

答：条件更新 `UPDATE orders SET status=20 WHERE id=? AND status=10`。rows=0 时再查一次：已是 20 说明重复支付，直接返回成功，不重复插 payment；其他状态抛异常。唯一索引 `uk_payment_no` 兜底。核心是"条件更新保证状态只迁移一次 + 重复请求识别为成功"。

> 考官想考察：幂等设计（条件更新 + 状态判断），而非只会说"加幂等键"。

**Q3：取消订单要回补哪些东西？**

答：状态条件更新（10→60）→ 回补库存（普通回 stock、秒杀回 seckill_stock 并 Redis INCR 预扣库存）→ 月销回减 → 退券（status 2→1）→ 失效商品详情/热门缓存 → afterCommit 同步 ES。回补与取消在同一个事务里，保证一致性。

> 考官想考察：对取消链路完整性的把握——不只会改状态，还要还库存、还券、刷缓存。

**Q4：订单状态机怎么保证并发下只流转一次？**

答：每次流转用条件更新 `WHERE status=from`，0 行说明并发下状态已被别人改过，抛 `ORDER_STATUS_INVALID`。`transition` 方法统一实现：查订单 → 归属校验 → 条件更新 → 0 行抛异常。这是状态机的乐观锁实现，比悲观锁（SELECT FOR UPDATE）轻。

> 考官想考察：状态机的并发正确性，条件更新做乐观锁。

**Q5：为什么下单要发消息却放在事务提交后？**

答：如果事务内发消息，事务回滚时消息已发出，消费者会处理一个不存在的订单（脏数据）。用 `TransactionSynchronization.afterCommit` 保证"订单确实落库才通知下游"。这是 MQ 与 DB 一致性问题的最小解法，生产可升级为本地消息表 + 定时补偿。

> 考官想考察：分布式事务/最终一致性的入门——为什么 afterCommit。

**Q6：无权查看订单为什么返回 404 而不是 403？**

答：防探测。403 会让攻击者区分"订单存在但无权"和"订单不存在"，从而枚举订单号。404 把两种情形合并，不暴露资源存在性。`requireOwnerOrder` 和 `getDetail` 都是这个策略。

> 考官想考察：安全意识——资源存在性也是信息泄露面。

**Q7：@IdempotentSubmit 是怎么防连点的？原理和局限？**

答：AOP 切面用 Redis SETNX，key=`citygo:idempotent:{userId}:{requestId}`，首次放行设 TTL 10 秒，重复提交抛 409。它防的是"同一请求号窗口内重复提交"，是接口层去重；局限是依赖客户端带 X-Request-Id，且只是窗口内去重，真正的业务幂等还得靠扣库存条件更新。

> 考官想考察：对幂等与防重的层次区分（接口层防连点 vs 业务层幂等）。

## f. 开发实战扩展

1. **延迟消息升级**：afterCommit 发消息是简化方案，生产用"本地消息表 + 定时任务补偿"或 RocketMQ 事务消息保证发消息与 DB 提交的最终一致。
2. **库存独立服务**：高并发下库存扣减抽成独立库存服务（Redis 预扣 + 异步落库），订单服务只负责订单，解耦削峰（秒杀场景 11 篇就是这么演进的）。
3. **分布式事务**：下单涉及库存、优惠券、购物车多个资源，生产跨服务时用 TCC/Saga 保证最终一致。
4. **订单分库分表**：orders 大表按 user_id 分片，order_no 做全局路由，查询用 ES 索引（本项目已有 ES 搜索雏形）。
